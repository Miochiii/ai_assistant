# 多步指导定位修复：第二步，窗口几何变化使旧框失效

## 本次行为变化

1. 修正 PanelSession watch 截图中的条件分支。原来仅在“几何相同、像素变化”时清框，几何不同时反而进入旧框续期分支。现在窗口移动、尺寸变化、前台对话框切换或绑定窗口几何变化都会先清框，然后才走 resumeAfterCapture，不再主动恢复这张旧框。
2. 从截图到绘制传递 window_geometry。记录主窗口以及不同于主窗口的前台窗口各自的 HWND 和可见边框（left, top, right, bottom），最多两项。首次桌面识别路径也补齐此记录；后续步骤由 parseVisualReply 携带，经过 ResidentHost 和 HighlightController 传到 overlay。
3. 绘制层每轮检查记录中的每个窗口是否可见、未最小化、可见边框一致。窗口移动或缩放后，旧框在绘制循环中隐藏，无需仅依赖约 2 秒一次的 watch。绘制循环为约 150ms 调度，不是实时截止时间保证。
4. frameGeometry 纳入各窗口边框：即使主窗口与对话框并集不变，内部窗口移动也能判为几何变化。

## 坐标约定

截图的 visible_frame 优先使用 DWM 可见边框；原 overlay.window_rect 使用 GetWindowRect。不能把两种边框直接比较，否则隐藏的调整大小边缘可能导致一直误判变化。

新 window_geometry 校验与截图复用 visible_frame；保留旧 window_rect 输入的原有检查，兼容旧的观察文件。新字段不是截图裁剪区域，也不是主窗口与对话框的并集。主窗口和对话框逐个验证，负坐标屏幕有效。

没有移动旧坐标去“追随”窗口：几何变了就隐藏，由稳定后的观察重新定位。仍未解决同窗口内小范围像素变化漏检、watch 面板遮挡、模型中心精度与固定 36×36 指示框问题。

## 修改处

- panel-session.js：几何变化先清框。
- watch_window.py：捕获主窗口/前台窗口独立可见边框。
- desktop-grounding.js、panel-model.js、visual-target.js：首次绑定与后续步骤携带几何。
- task-watch.js：几何比较覆盖独立窗口。
- resident-host.js、protocol.js、highlight-controller.js：传递并验证 window_geometry；目标 HWND 必须在绑定列表中。
- coach_overlay.py：绘制前逐窗口检查可见边框。
- test_desktop_grounding.mjs、test_assistant_highlight.mjs、test_highlight_geometry.py、test_watch_window.py：回归测试。

## 验证结果

35 项 Node 测试通过（desktop_grounding、assistant_highlight、task_watch、assistant_panel_guidance、assistant_panel_model）。覆盖移动、缩放、前台对话框切换、并集不变但内部窗口变化、无变化时保留框，以及完整几何传递链路。

3 项绘制层 Python 测试及 7 项窗口捕获绑定测试通过：负屏幕原点、移动/缩放拒绝、主窗口与对话框分别校验、丢失窗口和未绑定目标拒绝，以及现有前台绑定行为。使用 E:\python\python.exe（overlay 运行解释器），mock Windows 查询，不创建 Tk 窗口。首次使用工作区 Python 的受限测试因 ctypes DLL 加载失败，未执行测试断言；改用实际绘制解释器后通过。

全部为离线测试，没有请求 API、截图或操作真实桌面。测试目录由 finally 清理，合成面板计时记录已删除。真实效果待 Harness 完整重启后验收：展示提示后移动/缩放窗口，旧框应隐藏，不应跟随旧坐标续期；重新稳定后再由指导观察定位。
