# 指导窗口前台绑定修复

用户首次验收“教我如何在记事本中换字体”收到 `GUIDANCE_WINDOW_NOT_FOREGROUND`，任务尚未建立。现场没有记录足够的前台元数据，无法从该截图断定当时究竟是窗口切换、隐藏所有者窗口还是实际切到了其他窗口。

本轮只读对照发现：截图使用的 Python 3.14.9 和桌面 Python 3.12.6 均能读到相同的当前前台 HWND、PID 和可见状态，没有复现解释器间的桌面访问差异。没有重设完整性标签或修改环境。

代码修复：

1. 初始绑定改用 `GA_ROOT` 的实际可见顶层窗口，不用可能不可见的 `GA_ROOTOWNER` 宿主。已绑定任务通过有界 `GW_OWNER` 链识别所属弹窗，其他同 PID 窗口也不会被自动接受。
2. 在 mss 调用中显式排除 Orb 和高亮进程 PID，防止自身窗口被当作指导目标。
3. 助手隐藏后，前台为空、不可见或仍是助手时，最多等待 1.2 秒，每 50ms 只读复查。不激活软件、不点击、不强行切换焦点。已绑定窗口真的被替换、最小化或 PID 变化时仍拒绝。
4. 截图后继续核验归属和几何，截图中途发生变化仍拒绝结果。
5. 面板显示中文原因和恢复方法，不再把 mss Python 异常栈直接展示给用户。失败时另写 `runtime/assistant-panel/<session>/capture-diagnostic.json`，区分初始绑定和已绑定窗口阶段；不包含截图、窗口标题或对话正文。

测试：11 项 Python 模拟窗口绑定/像素差异测试通过，覆盖隐藏宿主、所属弹窗、助手自身排除、短暂切换重试、真实换窗口不重试及等待上限。相关 Node 回归通过。未调用模型 API，未进行真实记事本交互验收。

## 2026-11-08 补充：动态壁纸被误判为目标窗口

live 失败为“目标窗口画面已变化，请重新指导”，但用户只看到动态壁纸变化。代码根因是
全桌面视觉绑定层最初只按坐标取可见窗口，没有排除 shell/桌面/系统悬浮层：

- `Progman` / `WorkerW` / `Shell_TrayWnd`
- `NVIDIA GeForce Overlay` / `Microsoft Text Input Application`
- tool window、空/系统标题窗口

这些窗口可能覆盖目标点，绑到壁纸后壁纸动画会被当成“目标窗口变化”。

已补：

- `watch_window.visible_windows()` 返回 class/title/owner/tool_window 元数据
- `desktop-grounding.eligibleWindow()` 过滤 shell、桌面、系统 overlay、tool window
- `selectVisualWindow()` 在目标点或窗口点落在不可操作层时明确拒绝，不再绑定壁纸
- 变化错误带 `hwnd/class`，便于判断到底绑了谁

回归：`tests/test_desktop_grounding.mjs` 6 项、Node 全量 223 项通过（此前该测试文件
有一个未收尾的语法错误，已修）。仍未进行真实动态壁纸/记事本 live 验收。

另一个现实限制：如果记事本被 DSH/Orb 完全遮挡，整桌面截图里根本没有记事本，
模型无法可靠识别；上游 Orb 的可靠路径是操作前台 eligible 应用窗口，而不是从整桌面
任意窗口里猜。先让目标软件完整可见再验收。

## 2026-11-08 补充：DPI 坐标错位与线路 A

进一步核对发现：

```text
GetWindowRect（DPI unaware）: [773,126,1333,545]
DWM visible frame（物理像素）: [1170,189,1990,808]
mss 截图坐标: 物理像素
```

Python helper 未声明 Per-Monitor DPI awareness，窗口矩形是逻辑坐标，而截图是物理像素；
`cropWindow` 因此裁到错误区域（壁纸/其他窗口），即使 hwnd 已经是 Notepad，也会报
“目标窗口画面已变化”。

修复：

- `watch_window.set_dpi_awareness()` 在 Win32 查询前启用 Per-Monitor V2
- `visible_frame()` 优先 DWM `DWMWA_EXTENDED_FRAME_BOUNDS`，避免不可见边框
- `visible_windows()` 返回 DWM 可见框、class/title/owner/tool_window
- `desktop-grounding.eligibleWindow()` 拒绝 shell/桌面/系统 overlay
- 默认指导截图改为 **线路 A：隐藏助手后取前台 eligible 应用窗口**；
  `captureMode=desktop` 保留全桌面视觉绑定作为可选实验路径
- 线路 A 现场发现前台可能是视频浮窗；默认已改为 **全桌面视觉定位**，
  `captureMode=foreground` 保留为可选路径
- 模型回复后的新鲜画面复核改为 `watch:false`，避免用户还在 Orb 输入时被焦点门控误拒

这样壁纸不属于目标窗口 crop，且窗口坐标与 mss 都是物理像素。仍需重启 Harness 后
在记事本完整可见时做真实 live 验收。

补充：线路 A 首次仍报 `assistant_still_foreground`。原因是隐藏 Orb 后
`GetForegroundWindow` 仍可能指向隐藏的 Orb。初始未绑定任务现在会在
`GUIDANCE_WINDOW_NOT_FOREGROUND` 时回退到全桌面截图，再走视觉窗口绑定；
已绑定任务仍严格要求目标窗口可见，不跟随到其他软件。对应测试
`foreground capture falls back to desktop when Orb remains foreground` 通过。

### 线路 A 的第二个现场问题

用户复测时 Notepad 实际可见，但隐藏 Orb 后前台是**视频通话浮窗**，线路 A 只截到
视频通话画面，模型因此说“截图里没有记事本”。这不是模型或 DPI 的问题，而是
“前台 eligible 窗口”不等于“用户目标窗口”。

因此默认入口改回 **全桌面视觉定位**：全桌面截图里同时看到 Notepad、视频浮窗和
壁纸，由用户文字与模型视觉选择 Notepad；DPI/DWM/shell 过滤继续生效。线路 A 仍
保留为 `captureMode:'foreground'` 选项，并在失败时回退全桌面。



加载方式：本轮含 Host JavaScript 修改，需完全重启 Harness。让记事本处于前台，再通过悬浮球输入同一指导请求。若仍失败，读取上述诊断文件确认阶段与具体拒绝原因，不继续扩大截图范围或取消窗口约束。

## 复用 Orb 窗口 eligibility

已复制 `windows-foreground.ts` 到 `plugins/dsh-assistant-host/vendor/orb/vision/`
作为参考副本，并做最小 JS 适配 `eligibility.js`：保留 shell/overlay、
tool window、cloaked、最小尺寸过滤。全桌面回复现在只要求 target 点，
本地用 target 点选 eligible 窗口；不再要求模型额外给 window 点，也不再
做两个点必须同一 HWND 的绑定。鼠标/键盘动作没有复用 Orb，仍不自动执行。

## 首步提示与计划不一致

模型常把顶层 `text` 写成“先打开格式菜单”，而 `steps[0].text` 写成“打开格式菜单”；
旧代码用严格字符串相等判断，导致整轮指导失败。

现在 `parseGuidancePlan` 接受这种措辞/标点差异，并把顶层 `text` 作为第一步提示，
后续步骤和 expected 完成条件保持模型原样。不会放宽步骤数量、expected 可见条件或
target 的校验。对应测试：`plans accept a top-level instruction that differs from step zero`。

## 助手闪烁与高亮不显示

两个原因：

1. TaskWatch 每 2 秒截图时都会隐藏 Orb，造成面板闪烁。已改为：绑定窗口的 watch
   截图不再隐藏 Orb；只有初始全桌面/绑定确认截图隐藏。
2. TaskWatch 首次检查时用户还在 Orb，目标窗口不在前台会抛
   `GUIDANCE_WINDOW_NOT_FOREGROUND`，旧 catch 立刻 `clearHighlight`，所以高亮
   从未显示。现在“用户正在助手面板交互/目标暂时不在前台”只进入 waiting_window，
   保留当前高亮；真实截图/内容失败才清除。首次从全桌面基线切换到目标窗口 crop
   也不再误判为画面变化。

测试：`temporary Orb focus keeps the current highlight and waits` 通过。
