# 常驻记忆检索与分段计时：实现与交接

日期：2026-11-09。前置验收：用户已确认次日自动整理、显式查询、同工作区新会话自然语言召回正常。本次针对每次自然语言查询重新加载 BGE 的延迟，不改变每日整理规则、模型选择或桌面动作能力。

## 已实现的调用链

```text
面板普通对话
  → daily_ingest（原有记录策略）
  → Host rag_recall
       → SQLite rag_snapshot：当前有效记忆、scope、version
       → 常驻 Python worker：BM25 + BGE + 按现有条件重排，仅返回 ID
       → SQLite rag_resolve：复核 scope / version / 有效性，读取当前正文
  → 发送前 rag_version 校验
  → 隔离的 DeepSeek 模型请求
  → 返回后 rag_version 校验
  → 展示完整回复
```

SQLite 仍是权威数据源。进程复用只保留模型实例；没有新增回答缓存或召回结果缓存。每次请求仍单独打开/关闭 Qdrant，沿用快照代次及 Windows 文件锁。

### 生命周期与故障处理

- 每个 Memory Host 惰性启动一个 CPU worker，使用 stdin/stdout 的逐行 JSON 和随机 request_id，不开放网络端口。
- 请求串行；默认 80 秒检索截止时间包含排队时间。面板原有总超时不变。
- 当前请求取消或超时：终止该 worker，下次需要时重建。排队请求取消：立即返回，不终止其他正在执行的请求。
- 进程退出、协议异常或检索失败：本次回到 SQLite 的当前有效条目做字面匹配；不再启动另一个重量级检索进程重试。取消请求不执行此降级。
- 空闲 5 分钟释放模型；插件卸载时释放。关闭面板不等于立即卸载 Memory Host。释放后第一次查询仍有冷启动成本。
- `memory-v2.json` 配置变化，在下一次检索前重启 worker。模型权重原地替换但路径、配置不变时，需要重启 Harness，当前不持续扫描权重文件。
- 协议输入/输出有大小限制，worker stderr 不写入面板或计时文件。

### 撤销与作用域

- 索引作用域同时绑定用户、工作区和 SQLite 数据库路径，测试数据库不能共用正式索引。
- resolve 只接受当前 scope、当前 version 下有效的候选 ID；正文由 SQLite 读取，不采信 worker 提供的正文。
- 版本指纹加入自动记忆 consent revision，因此关闭后再开启也会使在途旧快照失效。
- 撤销、源删除、版本变化返回空结果或 revision_changed；原有模型请求前后校验仍保留。
- 这是逻辑失效保证，并不等于安全擦除 RAM 或清理所有旧磁盘索引代次。旧索引物理清理仍属后续保留/删除策略工作，不把本次优化描述成已完成物理删除。
- 原有单次 CLI `rag_recall` 保留兼容。生产面板通过 Host 走新路径；单独调用旧 CLI 仍是单次进程，不能用它验收热查询性能。

## 分段计时

面板最后一次普通对话记录在 `runtime/memory/latency/latest-panel.json`，只保留一份，临时文件原子替换后清理。不包含问题、回复、记忆正文、会话 ID、密钥或截图。

| 字段 | 含义 |
| --- | --- |
| ingest_ms | 对话记录写入 |
| recall_ms | Host 召回总时间 |
| retrieval.snapshot_ms / resolve_ms | 两次 SQLite CLI 调用 |
| retrieval.queue_ms / roundtrip_ms | worker 排队 / 含排队与通信的总时间 |
| retrieval.import_ms / index_ms | 模块导入 / 建索引或恢复本地检索结构 |
| retrieval.embedding_load_ms / reranker_load_ms | 本次实际模型加载时间 |
| retrieval.bm25_ms / vector_ms / rerank_ms | 检索内部阶段 |
| retrieval.cold_embedding / cold_reranker | 请求开始时模型是否尚未加载；不代表该次一定会用它 |
| version_checks_ms | 模型请求前后版本复核总时间 |
| first_text_ms / model_total_ms | 模型首个文本增量 / 整个流结束时间，从模型请求开始计 |
| total_ms / status / engine | 面板完整处理时间、完成/失败、召回引擎 |

这些字段存在包含关系，不能全部相加。例如模型加载已包含在 index/vector/rerank 阶段中，roundtrip 也已包含 queue。首字时间不等于 UI 已显示文本：目前仍收齐并复核后展示，避免生成期间撤销的旧记忆内容提前泄露。只有 block-end、没有 text-delta 的模型响应可能没有 first_text_ms。文件写入自身的耗时不计入 total_ms。

## 本机验证结果

全程未调用付费 API，未安装依赖或 CUDA，未修改原 RAG 项目与环境。使用现有 Python 3.12 解释器和本地权重，CPU 推理。

| 测试 | 冷查询 | 同进程热查询 | 说明 |
| --- | ---: | ---: | --- |
| 15 条合成记忆，真实 worker | 16.073 秒 | 0.745 秒 | 冷查询包括建索引；热查询仍执行向量与重排 |
| 1 条合成记忆，真实 Host 全链路 | 13.508 秒 | 0.408 秒 | 含 SQLite 快照、worker、SQLite 复核；热 worker 本身 0.044 秒 |

15 条热查询的 embedding/reranker 加载时间均为 0；进程 PID 不变；第一名正确命中合成的 PyCharm 条目。1 条 Host 测试随后撤销该记忆，再检索返回空，版本发生变化。

这是单机小样本测量，不是 P50/P95，也不是 DeepSeek 对话总延迟的承诺。用户此前 55 秒的回复没有分段记录，不能反推其所有等待来自检索。

检查结果：

- Python `test_memory*.py`：61 项通过。
- Node memory/client/panel/daily/stream 相关测试：32 项通过。
- 覆盖串行复用、排队取消、在途取消、错误响应 ID、退出/超时恢复、配置变化、空闲释放、关闭后拒绝新请求、撤销、源删除、跨 scope/数据库、关闭再开启 consent、推理期间撤销后禁止展示。
- 两个真实本地 smoke 测试通过，报告保存在 `results/memory/resident-worker-smoke.json` 和 `results/memory/resident-host-smoke.json`。
- 初次受限环境测试因 Windows 子进程/临时目录权限失败；在获准的本地执行环境重跑通过。本轮产生的 15 个空临时目录及 smoke 测试数据库、索引已清理。

## 用户验收与后续顺序

Harness 的两个插件目录仍 Junction 到本项目；无需重新安装。方便时完整退出并重开 Harness，以加载新模块。在助手面板连续询问两个已知偏好问题，间隔不超过 5 分钟，比较第二次回复；不要仅用“查记忆：”命令测 RAG，该命令走显式字面查询。随后查看 latest-panel.json 分辨 recall 与 model_total 的占比。

下一步以真实计时为依据：若模型等待占主导，先检查请求长度/模型端耗时；若热检索占主导，再评估重排调度和精确偏好直达。不为提速删掉撤销或作用域检查。

记忆功能后续优先补齐：旧索引/事件的保留与删除、冲突偏好的更新流程、带来源和时间的事实/事件记忆、召回质量评测。每日自动整理仍按已验收规则运行；本次不扩大无人工确认的自动采纳范围，也不把影子变点报警改成自动删库或重建指令。
