# 新开发主线：手机远控时，用文字让 Orb 完成电脑操作

更新日期：2026-11-12。用途：后续 DS / Codex 的主线交接与选型依据。

## 1. 用户目标与本次决策

用户经常在外面用手机经 UU 远控电脑开发。手机上找按钮、切换键盘、输入路径和命令成本高。目标是：**用户只需给 Orb 发文字指令，Orb 打开对应软件并完成操作，把手机端手工操作减少到必要的指令、确认和接管。**

用户已验证各项基础能力，陪伴暂时收尾。不要重新从“是否能截图、点击、输入”开始造基础设施；当前最重要的技术瓶颈是点击精确度，以及组合操作在真实界面变化下的可靠性。

本文件承接用户最新方向。旧 docs/project_goals.md 中通用定位、动作验证、流程复用的原则继续有用，但其中“部分输入能力尚未实现”“定位第二线暂缓”等历史阶段结论，不应压过本次用户决定。旧文件未在本次修改，后续执行者须以最新任务与当前激活代码为准。

本次仅制定路线和调研；未安装新模型，未改运行代码，未测得任何点击准确率提升。

### 本阶段做与不做

- 做：精确定位增强、可靠输入、常用软件/项目入口、重要操作流程复用、执行结果回执。
- 不另建手机 App、不替换 UU；指令仍发给电脑上的 Orb。
- 不新建完整 Teach。遇到不能定位时可保留单步提示/人工接管，但不能把日常任务重新变成用户逐步点击。
- 不扩展陪伴自动记忆。用户担心 DS 看屏不准是明确约束：屏幕观察和视频台词不能自动变成个人事实。
- 不要求开发时不断重测已验收功能；只针对修改路径做回归，并新增真正缺失的精度/端到端证据。

## 3. 总体架构：规划与定位分开，动作仍走原 Orb

```text
手机上的文字指令 → Orb 原生会话
  → 解析目标、软件、项目和完成条件
  → 读取相关的已确认入口/流程
  → 选择操作方式
      A. 软件启动参数 / Shell / 文件 API / 已验证快捷键
      B. GUI：观察 → 目标定位 → 坐标映射 → 点击/输入
  → 验证真实结果
  → 下一步 / 有界恢复 / 请求必要接管
  → 简短结果回执
```

重要区别：A 可以减少不必要点击，但不能用“都改成命令”回避 B 的精度问题。打开指定软件/项目通常适合 A；软件内部按钮、复杂弹窗和专有功能仍需 B。

任务规划器输出“目标是什么、动作是什么、完成条件是什么”。定位器只处理“当前截图中这个目标在哪里”，不自行扩大任务范围。专用定位服务可以独立部署，但最终点击仍经过同一套 Orb 执行与取消流程。

## 4. 点击精度先分清问题，不只换模型

每次失败至少分成以下类别：

1. **目标理解错误**：要点运行，选成调试。换坐标转换公式解决不了。
2. **目标不可见**：按钮藏在菜单/折叠区域/滚动区，必须先展开、滚动或等待。
3. **视觉定位误差**：小图标、相似按钮、密集菜单和高分辨率缩图导致找错位置。
4. **坐标映射错误**：窗口图与全屏图混用、裁剪偏移遗漏、DPI 缩放重复处理。
5. **执行前状态改变**：窗口移位、弹窗遮挡、用户接管、焦点已变化。
6. **结果判断错误**：点击确实送达，却没有打开预期页面或完成任务。

位置记忆只能辅助 1–3，不能替代实时证据；训练定位模型也不能修复 4–6。

## 5. 文献与开源调研（2026-11-12 在线核对）

以下只使用作者论文页、机构页面和官方项目。不是穷尽所有新工作，也不宣称某模型是当前全局第一。论文基准成绩不等于用户 Windows/中文 PyCharm 的实测效果。

### 5.1 首选工程路线：候选区域 + 局部精定位

**OmniParser** 将截图解析成可交互区域和元素信息，可让规划模型选择候选，再由程序使用区域几何确定位置。本地已经有参考源码。它提供解析能力，不保证知道用户具体想选哪个相似按钮；检测框也不天然等于可点击区域。[官方仓库](https://github.com/microsoft/OmniParser)

本项目建议：先试 OCR/可用的 UIA 等轻量信息，必要时复用 OmniParser 补图标候选；只把与任务相关的小组候选交给 DS，不把全屏上百个编号塞入提示词。结构化信息可用时作为增强，不恢复“每个软件一套专用底层”的旧路线。

**Visual Test-time Scaling / RegionFocus（ICCV 2025）** 研究在推理时选择、放大区域以改善高分辨率界面定位。本次论文可访问，但论文给出的 RegionFocus GitHub 地址返回 404，不能写成已可安装组件。可参考思想，不能计划依赖尚未取得的源码。[论文](https://openaccess.thecvf.com/content/ICCV2025/papers/Luo_Visual_Test-time_Scaling_for_GUI_Agent_Grounding_ICCV_2025_paper.pdf)

**DRS-GUI（CVPR 2026）** 用 Focus / Shift / Scatter 和搜索来选择相关区域，避免一次裁错后越缩越错。本次核实了论文，未确认可用官方代码；完整搜索增加成本，先借鉴“裁剪失败可退回全图/换区域”，不直接复制 MCTS 搜索到每次点击。[论文](https://openaccess.thecvf.com/content/CVPR2026/papers/Liu_DRS-GUI_Dynamic_Region_Search_for_Training-Free_GUI_Grounding_CVPR_2026_paper.pdf)

**选择理由是本项目工程判断**：这一条容易接入原 DS 规划器，无需先训练或替换整个助手，也方便定位精度与 token 的对照。

### 5.2 专用定位模型：作为第二组对照

**GUI-Actor（NeurIPS 2025）** 使用注意力动作头定位视觉区域，而非仅把坐标当文本生成；配套 verifier 选择候选区域。代码、权重入口已公开，值得作为专用 grounding 对照。但需要模型自身结构/权重，不能只给 DS 加一句提示词就获得这种能力。[官方仓库](https://github.com/microsoft/GUI-Actor)

**GoClick（2026）** 将任务规划与元素定位分开，论文提出轻量定位模型；作者提供代码和 GoClick-Large 权重。适合探索“DS 描述目标，本机小模型定位”。但公开示例包含移动端和网页任务，本机 Windows IDE 效果未验证；论文的 230M 描述不能直接套到名为 Large 的权重，实际参数、显存、许可证与推理依赖需逐一核对。[论文](https://arxiv.org/abs/2604.23941)、[代码](https://github.com/ZJULiHongxin/GoClick)、[权重](https://huggingface.co/HongxinLi/GoClick-Large)

**UI-TARS** 有专门 GUI 模型和公开运行工程，可作为另一基线；仅接定位适配，不为测试它迁移整个产品。区分原版、1.5 与具体权重大小，不能混用排行榜数字。[官方仓库](https://github.com/bytedance/UI-TARS)

历史机器记录为 RTX 3070 Laptop 8GB / 16GB 系统内存，部署前重新核实。不能保证 7B 模型在截图高分辨率、KV cache 和其他应用共同占用时可用；量化后也需复测精度。优先独立环境与按需运行，不改已有 ASR/RAG Python 环境。模型卡自动生成的部署示例不等于已验证 Windows 兼容性。

### 5.3 针对 IDE 密集目标的前沿方向

**PrecisionCUA / See, Point, Refine（2026）** 是代码编辑器精细定位研究，公开了 VS Code 数据采集和多轮视觉反馈评测。仓库中有预测点标记后再纠正的流程。它是研究/评测代码，不是可直接装进 Orb 的通用点击插件；其正确性判断依赖评测真值，生产环境没有该真值，不能照搬“知道点错再重试”的结论。[机构论文页](https://www.microsoft.com/en-us/research/publication/see-point-refine-multi-turn-approach-to-gui-grounding-with-visual-feedback/)、[官方代码](https://github.com/microsoft/precision-cua-bench)

本项目借鉴：点击之前可在截图副本上标记候选点并做一次局部核对；不要先真实点击未知按钮来获取纠错反馈。同模型自检不等于独立验证，须以消融试验确认收益。

**IGG（2026）** 研究目标必须先被展开、移出遮挡、滚动到可见等情况，提醒我们不能只测静态已可见按钮。这与 program 文件夹展开后才出现 PyCharm 的真实问题吻合，但其网页基准不直接代表桌面效果。[作者项目页](https://igg-bench.github.io/)、[论文](https://arxiv.org/abs/2610.32536)

### 5.4 本次推荐排序

| 顺序 | 方案 | 目的与限制 |
|---|---|---|
| A | 坐标链核对 + 候选区域 + 一次局部精定位 | 第一实施路线；改善小目标定位，保持 DS 与原执行器 |
| B | 单独比较一个专用 grounder | 先 GoClick 或 GUI-Actor 小模型，按实际可部署性二选一，不同时常驻多个模型 |
| C | 有界视觉反馈核对 | 只给困难目标加一次请求，测收益而非默认每步多轮 |
| 暂缓 | 自训、完整区域搜索树、全新代理框架 | 当前先把个人任务做准，避免训练和维护开销 |

这些是设计建议，不是已经测出的优劣。没有一个候选可承诺“不会点错”。

## 6. 定位增强的具体执行逻辑

建议建立小型 grounding adapter，先与原 click 并行做只读结果对照，再通过配置开关接入。

输入建议包含：observationId、原图尺寸、窗口/屏幕标识、截图几何版本、目标名称、动作类型、上下文锚点。输出包含候选 bbox/point、坐标空间、来源、是否可见、是否有歧义、有效期/关联观察。以上是建议接口，不是当前已存在工具。

流程：

1. 确认窗口、目标是否可见；不在当前画面时规划必要的展开/滚动，取得新图。
2. 先生成相关候选；可直接识别唯一文字按钮时用其边界。
3. 对密集/小图标裁剪局部，再做精定位；保留必要邻近标签，不能裁得失去上下文。
4. 候选必须匹配动作和标签。重叠候选、相似图标或错误区域不能仅靠模型自报“置信度 0.99”放行。
5. 在实际可点击区域内部取点；避开分隔线、边缘和邻近危险控件。不规则目标不能机械取检测外框中心。
6. 映射回原截图，再通过原生 Orb 坐标适配进入现有 click。
7. 点击前确认观察仍有效；窗口移动、尺寸/焦点变化或用户输入导致失效时重取图，不沿用旧点。
8. 只执行一次动作，验证结果；失败区分误定位、未响应与页面加载，不盲目重复点击。

### 坐标必须有明确归属

当前 Orb 工具对模型暴露归一化位置，实际实现须以当前 SCREENS/COORDINATE_FIELDS 及 backend 为准，不能照抄旧 Python 执行器的原图像素协议。

假设局部图没有 padding，裁剪在原截图中的起点为 `(x0,y0)`，宽高为 `(w,h)`，缩放到 `(Wc,Hc)`；预测局部像素 `(u,v)` 回原图为：

```text
x = x0 + u * w / Wc
y = y0 + v * h / Hc
```

有 letterbox 时先扣除 padding 再逆缩放；多层裁剪逐级组合变换。转换到 Orb 所需的 0–1000 坐标只做一次，并严格匹配它所绑定的原截图。全屏原点、前台窗口原点、客户区原点不能混用；物理像素不能重复乘 DPI。

**UU 手机端的显示缩放不是电脑端定位坐标系。** 助手应从被控电脑本地采集并执行；只有远控实际改变了电脑分辨率/窗口几何时才更新映射，不能用手机画面尺寸换算电脑点击。

首版预算建议：一次常规定位，困难时最多一次额外局部请求。仍不明确则报告具体阻塞或给用户两个明确选项，不无限细分截图。

## 7. 软件/项目记忆与操作流程

复用 Memory Evolve 保存用户确认的映射：

- 软件别名 → 正式名称、选定版本、可执行路径、启动方式。
- 项目别名 → 项目根目录、解释器/虚拟环境、常用命令、工作目录。
- 软件入口 → 菜单名称、区域/相对位置，作为辅助线索；坐标不是长期可靠事实。

路径每次执行前检查存在性。软件升级、移动路径或多个同名项目时重新解析/必要时询问，不偷偷猜一个版本。

已验证流程另存版本化的步骤定义，记忆只引用流程 ID/适用条件。流程包含参数、前置条件、目标语义、动作、完成条件和失败出口；不要保存盲点坐标序列。已有 PreAct 概念可复用，但是否适配原生 Orb 执行器要单独处理，不把旧样例 proof 当作新流程的有效凭证。

只有真实任务完成并验证后才能标记流程可复用；助手自述“记住了”或用户指出一个大概区域不等于流程验证成功。用户纠错可以更新映射，但不要自动修改可执行步骤后继续运行。

## 8. 首批端到端任务与手机交互

首批建议任务（参数取用户已确认配置，不预先虚构路径）：

1. “打开 PyCharm，进入我的某项目。”验证正确软件版本及项目身份。
2. “在这个项目运行测试，把失败原因告诉我。”验证工作目录、命令结束状态和结果，不仅是终端已打开。
3. “把这段多行内容填进指定编辑区。”验证目标、中文/换行与内容完整；输入不自动等于提交或执行。
4. “打开项目设置里的某个选项。”这是必要 GUI 点击的重点样例，要覆盖菜单、同名按钮和小图标。

普通已授权任务连续完成，只在缺少必要参数、存在真实歧义或不可逆关键操作时打断用户。用户可以发“停止”“做到哪了”“继续刚才任务”。结果只需说明做了什么、是否完成、若失败停在哪里。

不要要求手机用户逐步确认每个普通点击。用户手动切焦点或输入时应暂停冲突动作并保留任务进度；不能检测到“远控连接存在”就一律禁止自动操作。

## 9. 评价：精度与手机节省都要衡量

用户已验收基础能力；下面是新定位方案的定向对照，不是推翻已有验收。

建立个人开发任务定位集，建议第一轮 50 个目标、保留一部分只用于最终对照：PyCharm、资源管理器、终端、开发相关网页；文字按钮/小图标/同名目标/滚动后目标/弹窗分别标注。截图必须来自被控电脑，变化条件覆盖窗口移动、分辨率/DPI、主题和菜单状态。

基线：现有 Orb；实验 A：候选+局部定位；实验 B：一个专用 grounder；有实际需要才加实验 C。相同截图、指令和标注比较，调参集与最终集分离。

- 定位命中率：预测点在人工确认的实际可点击区域内。给出分子/分母和各类结果，不仅平均像素距离。
- 可见性判断：目标不存在/不可见时是否正确拒绝，而不是随便输出坐标。
- 真实点击与任务成功率分别记录；拒绝率、恢复次数、误点次数单列。
- 手机端每个任务的人工点击数、键盘切换次数、重复解释次数、接管次数，与原手动方式比较。
- 记录单步/任务耗时、额外截图和模型请求、token、峰值内存/显存。先测后定上线阈值，不把建议指标写成实测成绩。

公共补充基准可采用 [ScreenSpot-Pro 官方评测](https://github.com/likaixin2000/ScreenSpot-Pro-GUI-Grounding)，它针对专业高分辨率界面；但静态命中不代表连续操作成功。不要跨论文版本和不同设置直接拼“冠军榜”。

上线门槛：个人任务集相对原基线有明确改善，真实连续任务的误点不增加，额外耗时/调用成本可接受，可关闭新定位器回到原路径。拒绝所有困难样例虽然安全，却不能冒充精度提高；必须同时报告覆盖率。

## 10. 实施阶段与交付要求

**P0：固定当前基线与诊断。** 记录激活版本，确认现有坐标链，整理用户已有失败点击样例，建立小型个人定位集。不扩大基础能力验收范围。

**P1：点击精度增强（主优先级）。** 接入候选区域/局部精定位适配器，验证裁剪逆变换、歧义与观察失效，使用现有执行器；保留开关与原路径。
