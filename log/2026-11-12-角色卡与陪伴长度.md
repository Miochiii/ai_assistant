# 角色卡与陪伴长度（`.14`）

日期：2026-11-12。开发包 `dsh-orb-mio-dev` 0.2.1-mio-dev.14。

## 1. 做了什么

- **角色卡**：一张全局人设 + 可选的"指导单独"人设，存在 `runtime/character/character.json`，设置页「角色」卡可编辑，保存即生效（进程内缓存 `currentCharacter()`）。
- **注入范围**：只作用于 Orb 自己发起的调用 —— 面板聊天（`panel-model.js`）、屏幕陪伴（`orb-companion.js`）、指导（`panel-guidance.js`）。**不动 DSH 主会话的预设 system**。
- **注入顺序**：`角色卡正文 → 边界句 → 模块原有硬约束`。边界句固定为"角色卡只决定人设与语气；与下面的输出格式、能力边界冲突时，以下面的格式为准"。一个字都没填时不注入，提示词与之前逐字节一致。
- **陪伴长度**：`maxCompanionChars` 默认 60（20–120），`trimToSentence()` 按最后一个完整句子截断；输出预算 `maxTokens` 512 → 256（60 汉字 + JSON 外壳约 100 token，给紧会撞上限，而撞上限时 `companion-stream.js` 会整条丢弃）。

## 2. 为什么是 60 字

浮窗弹幕是单行滚动、字号 13px：中文约 13px/字，60 字 ≈ 780px，主屏 1707px —— 一行能完整显示。这也是"弹幕看不全"的直接原因：之前陪伴回复可到 1200 字，弹幕要滚动十几秒才走完，看起来就是被切掉。

## 3. 改动清单

`plugins/dsh-assistant-host/character-card.js`（新）、`orb-companion.js`、`panel-model.js`、`panel-guidance.js`、`dsh_orb_full_orig/client.js`（角色卡 UI + textarea 样式）、`dsh_orb_full_orig/dist/host/index.js`（`GET/POST /.dsh-orb/character`）、`tests/test_character_card.mjs`（9 项）、`tests/test_orb_companion.mjs`（+1 截断用例、maxTokens 断言改 256）。

测试：64 项全通过。

## 4. `.15`：人设统一到全局（复用 dsh-persona-dafeiyu）

用户实报：悬浮球面板里的对话就是工作区里那个主会话，所以只给 Orb 加卡覆盖不到它。结论是改用全局人设插件，Orb 这边只做"跟随"。

- 装了 `dsh-persona-dafeiyu@0.8.0`（npm / MIT，`plugin_manager install_bundle`，**无需重启**即时生效）。它 `inject=['systemPrompt']`，注册 `dafeiyu:persona` 段，支持 global / workspace / session 三档；人设库 `<DSH_HOME>/storages/dsh-persona-dafeiyu/personas.json`（未落盘时用内置三套 "大肥鱼 / 阿茶 / 听澜"）。
- Orb 侧改动（`character-card.js`）：每 60 秒从 `http://127.0.0.1:<ctx.webServer.port>` 的
  `/api/dsh-persona-dafeiyu/{status,persona?id=}` 抄**当前人设**，作为 `persona` 的基准。
  - 端口用 **resolver 每次现取**，不写死：webServer 可能比本插件晚就绪。
  - 只认"插件启用 + 有 current + 未 globalOff"；关掉就清空，**不偷偷沿用旧文本**。
  - 我们的卡里填了人设 → 优先用它（那时才加「你的名字是…」前缀）；留空 → 跟随全局且**不加名字前缀**（避免"两个名字打架"，用户之前实报过）。
- 实测（真实桥，非假 fetch）：60ms 拿到 635 字人设，`externalId=dafeiyu`、`externalName=大肥鱼`；拼出的 system 以模块硬约束结尾、无名字前缀。
- 测试：68 项全通过（新增 3 项：跟随、覆盖、关闭/断连不沿用）。

**要重启一次**才加载 `.15`（这是插件宿主代码，不是热更新）。

## 5. `.16` / `.17`：屏幕陪伴的闪与"两行浮条"

**闪的根因**：屏幕陪伴每 2 秒截一次图，截前要把自己的悬浮球/面板 `setContentProtection(true)` 挡出画面、截完再关掉（`cloak`）。Windows 上这个调用**每调一次重绘一帧**，于是球和面板每 2 秒闪一下 —— 与"有没有输出"无关，和截图里"本地采样 15 次、发言 0 次"完全对得上。

- `.16`：球与工具条改成 `resting: win32`（与观察框一致，常驻屏蔽采集），并在 `cloak.sync` 里加 `entry.applied` 记忆（值没变就不再调用）。副作用：悬浮球不再进截图/录屏。

**两行浮条**（`.17`，按用户确认的"两条固定行、新句往上推，不跑马灯；面板不自动弹、点击才弹"）：

- 新窗口 286×58：`dist/helper/assets/companion-ticker.html`（磨砂、圆角 14、发丝边、`backdrop-filter`）。
- helper：`ensureCompanionTicker()` / `placeCompanionTicker()`（贴球左侧优先，放不下换右侧，夹在工作区内）/ 每 700ms 轮询 `~/.dsh/dsh-orb/companion-ticker.json`；停止后先淡出、3 秒隐藏。窗口 `setIgnoreMouseEvents(true)`、`focusable:false`、`skipTaskbar`、win32 常驻屏蔽采集。
- 宿主：`writeCompanionTicker()` 原子写该 json；`OrbCompanion` 新增 `ticker` 回调 —— start → 采样 0；每次 tick → 更新采样/发言；`reply` → 第二行换成最新一句；`stop` → `visible:false`。
- 为什么不走 overlay 消息通道：那条通道只暴露 `setObservationFrame` / `withCapture` 这类固定动作，为一条 UI 提示去加协议不值得；文件轮询坏了只影响浮条，不影响陪伴。

测试 68 项全过；跑测试时 `stop()` 已经真实写出过 `{"visible":false,...}`，说明宿主 → 文件这条路是通的。

## 6. `.18`：浮条自己的坑 —— overlay ack timed out

实报：屏幕陪伴一开始采样就停，日志 `采样失败：dsh-orb: overlay ack timed out`。

- 宿主每次截图前发 `overlay-capture`，**helper 必须在 1000ms 内回 ack**（`OVERLAY_GUARD_ACK_TIMEOUT_MS = 1000`）。
- 我第一版浮条是"轮询里看到要显示才 `new BrowserWindow` + `loadFile`"。建窗 + 首屏正好把那 1 秒吃掉 → 第一次采样 ack 超时 → 陪伴当场停（所以显示"本地采样 0 次"）。
- 修法（`.18`）：**启动后 1.2 秒预热建窗**（那时没有在途截图），轮询只做 `readFile` + `showInactive` + `executeJavaScript`；并把 `readFileSync` 换成异步 `readFile`，避免阻塞主进程。窗口建不出来就退化为不显示浮条，陪伴不受影响。

教训：**helper 的主进程时间是稀缺资源** —— 任何"重活"（建窗、读大文件、同步 IO）都不该落在截图等待 ack 的那 1 秒里。

## 7. `.19`：真正的元凶是 TDZ，不是建窗慢

`.18` 的"预热建窗"没治好 `overlay ack timed out`。继续查发现根因在**声明顺序**：

```js
startCompanionTicker();          // 1560 行：函数声明会 hoist，能调到
...
const COMPANION_TICKER_FILE = …  // 1565 行
let companionTicker = null;      // 1568 行：`let` 在 TDZ 里
let companionTickerTimer = null;
```

调用点在这些 `let` **之前**，函数体里一读 `companionTickerTimer` 就抛 `ReferenceError: Cannot access before initialization`。而这一抛，**这个工厂函数后面"返回消息分发对象"的代码就永远执行不到** —— 于是宿主发来的 `overlay-capture` 没人 ack，屏幕陪伴一采样就 `overlay ack timed out`，并且是"本地采样 0 次"。

修法：把启动调用**延后一拍**（`setTimeout(…, 0)` + try/catch），那时 `let` 已初始化；顺带保证浮条起不来也不会连累消息分发。

教训两条：
1. 在这种"一个大工厂函数里按顺序建窗口 + 返回分发对象"的结构里，**任何在返回语句之前可能抛出的代码都会让整个 helper 变哑**。新增的启动逻辑要么放在返回之后，要么包 try/catch 并延后。
2. 现象是"采样失败"，但病因在"消息分发根本没挂上" —— 看到 ack 超时要先怀疑 helper 后半段没执行，而不是纠结 ack 那 1 秒。

## 8. `.20`：悬浮球被自己挡没了 + 浮条太小太快

`.19` 之后陪伴能跑，但用户报三件事，全是 `.16`/`.17` 的副作用：

1. **悬浮球没了**：`.16` 为了消闪，把球也设成 `resting: win32`（常驻 `setContentProtection(true)`）。但这台机器上给**透明窗**设 content protection 后整扇窗**不渲染**，球就彻底看不见了。窗口枚举确认：helper 只剩一个 344×444 的 "桌面 agent" 面板，96×96 的球不见了。
   → 修法：球和面板**退出 cloak**（不再设保护），工具条也回 `resting: false`（同一风险）；代价是截图里会带上那颗球，用提示词补一句"角落的小球是你自己，不要评论"。
2. **一句话显示太短**：正文行改成**至少 5 秒**才换（新句排队，到点替换），状态行仍然实时刷新；直接换句时把排队中的旧句一起丢掉，避免覆盖回去。
3. **对话框比语句短**：浮条 286×58 → **360×92**，正文最多两行（`-webkit-line-clamp: 2`），字号 13.5px、行高 1.42。

## 9. `.21`：浮条挂到球下面

实报：浮条在面板左侧，而且面板一开一合它就横跳 —— 因为原先是"贴窗口左边"，而这个窗口**收起时是 96×96 的球、展开时是 344×444 的面板**（同一个 BrowserWindow）。

- 改成**挂在球下方**、水平对齐球心；下面放不下才翻到上方。
- 定位用"**收起态**的 96×96"矩形：轮询时只要看到窗口是收起态就把它的 bounds 记下来，展开时继续用这份记忆 —— 所以面板开合不会再挪动浮条；拖动球时浮条会跟着走（收起态会被重新记住）。
- 从没见过收起态时（例如插件加载时面板就是开的），用 `defaultFloatingBallOrigin(workArea)` 推一个默认球位。

## 7. 已知限制

1. 角色卡只管"语气与人设"，改不了能力（陪伴没有工具、不能写记忆、不能录音）。
2. 极长的单句（用户把上限调到 120）在 1080p 以下的屏幕上弹幕仍可能超一行，仍会滚动；要彻底解决得让 `danmaku.py` 折行，本次没做。
3. 面板聊天的气泡显示上限（`resident-host.js` 的 140 字）没动 —— 那是面板气泡，与陪伴无关。
4. 角色卡不参与记忆写入与检索的内容筛选。
