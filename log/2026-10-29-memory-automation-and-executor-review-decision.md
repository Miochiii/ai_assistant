## 1. 决策结论

同意当前转向记忆自动化，分两批交付：

1. **自动 checkpoint**：宿主在确认的任务边界保存有来源、幂等、可关闭的工作上下文。
2. **按需自动检索与注入**：每条新用户请求做轻量路由，只注入相关、有效、获准使用的记忆。

不必每个实现步骤都询问 GPT。已有架构和授权边界内的实现、单元测试与缺陷修复可继续推进。真正扩大能力或改变信任边界时集中评审，而不是无限重复已有菜单案例。

| 键盘、文本、滚动、拖拽 | 开发前集中评审动作协议，然后分批开放；本轮不实现 |

## 3. 第一批：自动 checkpoint

### 3.1 同意状态由可信宿主持有

新增或复用项目级配置，分别表达 `auto_checkpoint` 与 `auto_recall`。以下是逻辑字段建议，不要求固定文件格式：

```text
consent:
  user_scope, project_scope
  auto_checkpoint: enabled | disabled
  auto_recall: enabled | disabled
  policy_version
  consent_event_id, updated_at
  retention_policy_id
```

同意必须来自用户真实命令或设置操作，绑定当前用户/项目；不得从页面内容、模型参数、记忆内容或自然语言推测制造。当前 `consent:true` 可以作为内部检查参数，但只能由宿主读取有效配置后构造，不能成为唯一授权证据。

用户一次启用后，在已声明范围内持续有效，无需每个任务询问。关闭后停止新自动触发；关闭本身不删除既有记录。配置缺失、损坏、项目不明、同意版本无法解释时自动化默认关闭，保留现有显式操作能力。

写入事务前再次检查启用状态，防止关闭后的排队任务继续落库。若写入已经提交，记录真实发生顺序，不声称关闭能撤销已提交数据。

### 3.2 触发来自任务生命周期，不是模型发言结束

首版仅接入已有可信 run/task 生命周期的任务，例如桌面运行。普通闲聊暂不推断“任务结束”，避免为覆盖所有对话再创建一个任务识别模型。

触发条件：

- 存在稳定的 user/project/task/run 身份和有效项目同意。
- 收到可信的 completed、failed、cancelled、timeout 或 interrupted 边界，并核对账本状态。
- 正常运行先完成执行器收尾、确认不再继续发送输入；宿主崩溃后若执行器存活状态未知，先处理运行恢复，不能误标“已停止”。
- 至少有新的可恢复内容，纯空记录不重复写。

不使用 token 流结束、assistant message/done、单个工具返回成功作为整个任务完成的替代。暂停等待用户可后续作为单独 checkpoint 原因，首版不需要扩展。

对于异常恢复，checkpoint 可以记录“是否仍有后台执行未知”，但恢复该检查点绝不允许自动继续输入。

### 3.3 首版不用额外 LLM 总结

从已有账本和工具回执确定性生成简短结构化内容：

```text
task_id / run_id / goal
termination_reason
completed_steps               # 只来自已记录的步骤结果
input_delivery               # sent / not_sent / unknown
verification                 # passed / failed / unknown + 验证范围
blockers
next_step                    # 待办建议，不是授权或可执行动作
evidence_refs
depends_on
```

沿用核心支持的 content/schema，不直接把示例字段全部塞入不兼容接口。确需扩展时先做 schema 兼容和迁移测试。

“菜单打开经过验证”不能写成“用户任务全部完成”。输入送达、程序条件通过、业务目标完成分别保留。模型自己的成功声明如需保存，必须标为声明，不覆盖宿主 verification。

不保存原始截图、整段对话、完整工具 stdout、密钥、旧坐标或授权令牌。证据保留引用即可；证据过期后检查点应显示 unavailable，不能补造内容。

### 3.4 来源必须可区分

至少区分：用户提出的任务目标、宿主运行事件、工具回执与验证结果、模型提出的待办建议。

现有 `userSource()` 可证明任务来自哪个用户消息，**不能证明 checkpoint 中的每一条执行结果也是用户亲口说过的**。优先复用核心现有来源类型；若核心不足以承载宿主来源，做最小 schema/API 扩展，不伪装为 `origin=user`。

来源 ID 从真实事件身份构造，重复投递稳定，禁止使用消息正文或敏感路径做可读 ID。没有真实来源身份时不自动落库，并返回可解释的失败。

### 3.5 幂等、失败与恢复

同一终结事件使用稳定 `operation_id`，例如由 scope、run、终结事件及 checkpoint 策略版本生成。不能每次重试都生成新 UUID。

- 同 operation、同内容：返回已有结果。
- 同 operation、不同内容：冲突，不覆盖旧记录。
- 写库失败：任务实际结果不变，账本记录 `checkpoint_write=failed`；只重试存储，不重跑桌面任务。
- 提交后进程崩溃、未回写账本：恢复时以同 operation 查询/重试，最终只一条 checkpoint。
- 已删除的 operation：保持删除语义，不换 ID 绕过 `OPERATION_DELETED`。

重试需有限次数、退避与取消检查；可暂存在运行记录中等待后续恢复，不要求引入常驻后台队列。显式报告保存失败，但不需要每次重试都向用户弹窗。

## 4. 第二批：按新请求自动检索与注入

### 4.1 触发粒度与路由

在每条新的用户任务请求开始时做一次轻量路由。网络重试/工具循环不重复建立新的召回批次；更换用户请求才使用新的请求身份。

优先复用核心的无需记忆路由和现有检索接口。首版可用保守、确定性的条件，例如明确要求接着任务、询问曾确认的项目约定；不为判断要不要检索再发一次模型请求。无法确定且确有相关需求时，模型仍可调用已有 recall 工具。

不把“每轮自动检索”实现成“每次都塞满固定数量记忆”。无相关结果就不注入。

### 4.2 召回范围

- scope 由可信宿主从用户/项目上下文计算，模型不能传任意路径切换项目。
- 自动检索仅使用当前有效、状态允许的事实/偏好等记录；候选、撤销、删除、过期和历史版本不自动混入。
- checkpoint 只在继续对应任务时作为工作上下文使用，不能作为长期事实检索的通用答案。
- 首版不自动跨项目、跨用户或跨任务拼接检查点。
- 同一事项冲突无法解决时保留冲突提示或不注入，不选择“看起来更合理”的值。

### 4.3 注入格式与预算

沿用 `context_only / execution_authority=false` 的数据标记；不把记忆正文放进 system 指令，不把其中的“下一步”转成已授权动作。

建议起始预算：最多 5 条、总正文最多 3000 字符，保留 memory_id、来源摘要、有效时间和作用域。此数值是可调整的工程默认，不是已验证最优值；超限返回截断说明和可展开引用，不能截掉关键否定/限制而不标记。

只使用当前 Harness 真实支持的请求上下文扩展入口，先核对接口与顺序；不得杜撰 hook 名称、伪造用户消息或工具执行记录来强行注入。不支持安全接入时，继续显式 recall，并列出具体阻塞点。

宿主应记录本次真正提交给模型的 memory IDs/版本；“准备了上下文”与“模型实际收到”要区分。若只能观测准备阶段，明确记录可观测限制。

### 4.4 依赖、撤销与失效

自动注入与显式 recall 共用请求级依赖登记。不是全会话无差别累积，也不能只记录最后一个请求：跨轮任务摘要若使用旧摘要或旧记忆，其依赖需要传递到新 checkpoint。

首版可采用保守依赖：记录构造 checkpoint 时实际使用的结构化结果/摘要所关联的全部记忆 ID，避免漏掉依赖；同时避免把完全无关的历史召回加进去。

注入前复核版本/状态。撤销或删除后，使待发送注入、缓存、派生摘要失效；请求已经发出则无法从服务端调用或历史对话中追溯收回，应阻止下一次继续使用并返回真实删除范围。

已有会话历史仍包含被删除记忆正文时，仅清本地召回缓存不够。核对宿主的上下文重建能力；无法剔除时明确提示该会话残留，必要时使用新上下文继续，不能承诺“模型已完全忘记”。

### 4.5 失败处理

检索超时、库不可用、相关性不足：继续无记忆处理，不阻塞无关任务。只有任务确实依赖缺失的历史信息时才说明并请求补充。

不因自动检索失败创建新记忆、不把失败结果负缓存为永久无记录。自动化异常不关闭既有显式命令；损坏数据库等实质错误仍如实报告。

## 5. 保留、关闭与删除语义

两批上线均需有可见的保留策略；不把“自动 checkpoint 已启用”解释成所有工作记录永久保留。

建议 checkpoint 默认可用期为 30 天，作为产品待确认的默认值；经启用界面/命令明确告知后生效，用户可调整。若暂未确定策略，先完成离线测试，不静默启用无限保留。

到期先停止自动召回，并生成保留/删除预览；首版不自动物理删除正文。**到期不可用不等于已删除**，如果还保留磁盘正文，界面必须明确说明。已有手动事实不因为 checkpoint 过期自动删除。

| 操作 | 语义 |
| --- | --- |
| 关闭 auto_checkpoint | 不再新增自动检查点；不抹掉已有记录 |
| 关闭 auto_recall | 后续请求不自动检索/注入；保留显式 recall |
| 到期 | 不再自动使用；不声称正文已经清除 |
| revoke | 内容不再作为有效记忆；依赖失效，按核心规则保留历史 |
| forget | 沿用 plan_id/data_version 绑定的删除，清除核心正文/索引及受控依赖 |

删除范围覆盖新增自动化缓存和待注入副本；不能通过队列重试、旧来源或重新导入复活已删除记录。审计只保留必要 ID/状态，不复制正文。Harness 历史、运行原始证据、用户导出等外部副本分别说明，不统一宣称已擦除。

不得为了删除记忆而直接删除程序库、proof 或独立运行证据。跨存储清理必须有单独范围与引用关系方案。

## 6. 最小验收与交付门槛

### 第一批验收

1. 未启用/项目未知时零自动写入；启用仅影响指定 scope。
2. completed/failed/cancelled/interrupted 分别保存真实状态，普通回复结束不触发。
3. 同终结事件重复投递、提交后崩溃恢复均只产生一条检查点。
4. 写库失败不重复执行动作；关闭后排队任务停止自动写入。
5. 用户目标与宿主结果有不同来源；没有来源不伪造 user 事件。
6. 依赖被撤销/删除后检查点按规则失效；删除 operation 不被重试复活。
7. 新会话能读取对应检查点，但恢复需要重新观察、重新核对授权，不自动执行。

### 第二批验收

1. 请求幂等；工具循环和网络重试不产生重复注入。
2. 跨项目、候选、过期、撤销、删除内容不自动召回。
3. 不相关请求可走 none；预算截断可解释；冲突不隐藏。
4. 记忆中的指令不能修改 system、授权或直接触发桌面动作。
5. 自动注入的依赖可追踪到 checkpoint，跨轮派生摘要依赖不丢失。
6. 删除/撤销发生在检索后、提交请求前时，有版本复核和失效处理。
7. 检索失败仍能处理不依赖记忆的任务；不默默把旧缓存当新结果。

先用隔离 SQLite、合成宿主事件和假请求提交器完成离线验收，再做一次有代表性的两会话现场测试。开发回归不需要反复调用付费模型。现场重点验证“真实触发和注入是否发生”，不能仅凭工具在列表中出现判通过。

交付记录应区分：接口完成、离线通过、插件已加载、现场通过；记录关键证据路径和已知限制。两批分别启用，不一口气开启所有自动化。

## 7. 后续执行器评审：提前确定的原则

默认多步失败 **fail-stop**：停止后续动作，保留已完成步骤和 input_delivery/verification 状态。不声称部分输入、文件保存或外部提交能够通用回滚。

补偿如果需要，必须是任务特定、单独授权且验证的动作，例如在明确条件下关闭刚创建的测试文档；它自身也可能失败。禁止把 Ctrl+Z 当作通用事务回滚。

进入键盘/文本/滚动/拖拽开发前，一次集中评审以下问题：

- key/button down 的所有权、成对释放、用户本来按住的键如何处理；不能释放不属于执行器的输入。
- 取消、异常、超时与进程强杀后的收尾；`finally` 不等于强杀时仍保证释放。
- 文本部分写入、IME/Unicode、焦点和选区变化、剪贴板方案的副作用与恢复边界。
- 请求去重与执行语义分离：只保证收到一次请求，不等于操作效果幂等；不宣称 UI exactly-once。
- 滚动量、拖拽路径/持续时间/边界、丢失焦点和用户接管的处理。
- 授权细分到输入类型、目标、任务和必要参数限制；新增能力不继承旧的 click 授权。
- 回执保留已发送事件、部分完成与 unknown，不将超时统一报告为“未执行”。

评审完成后按能力分批开放，无需每个函数都再问 GPT。

## 8. grounding 路线与后续决策边界

继续按[通用窗口技术设计](<E:/file/agent/ai assistant/log/2026-10-28-window-context-and-general-grounding-design.md>)执行：窗口元数据负责身份/几何，视觉负责界面理解，局部匹配为已知目标提速。

UIA/OCR 可在实际有收益且来源可靠时作为辅助，不必为“通用”排除所有系统接口，也不为每个软件写固定控件路径。不同来源保留来源和失败状态，冲突时不能无条件信任其中一项。

需要重新集中评审的变化：新增输入类型、跨项目自动记忆、自动 promote、自动物理删除、将记忆放入高权限指令、跨窗口授权扩张、自动补偿或更改 proof 信任规则。

不需要重新评审的工作：既定边界内的薄适配、幂等修复、字段校验、离线测试、已批准范围内的加载验收。DeepSeek 可直接推进，遇到实际接口缺失或边界冲突再提出具体问题。

完成后统一更新技术记录；运行账本和必要证据仍即时写入。测试临时数据库/目录在验收后定向清理，正式证据保留，不影响 RAG 环境和用户文件。
