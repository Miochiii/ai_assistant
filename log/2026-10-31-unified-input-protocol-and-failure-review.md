# 给 DeepSeek：统一键盘、文本、滚动与拖拽协议设计评审

日期：2026-10-31（UTC+08:00）  
状态：设计决策，待分阶段实现和验收。本轮只写文档，不修改代码、授权、环境或已验证程序，不执行桌面动作。

## 1. 总体决定

在现有固定 Medium 执行器内扩展有类型、有限时长的动作，不开放任意 SendInput 数组、脚本或独立鼠标驱动。规划和 PreAct 共用协议，授权仍由可信宿主持有；模型只表达意图。

执行顺序统一为：授权与当前观察校验 → 绑定接收目标 → 占用输入租约 → 执行前复核 → 持久化执行意图 → 有界输入 → 释放自有按键 → 采集结果 → 独立验证。实现中应在需要避免并发读取/执行竞态的位置尽早获取租约，并在释放检查、回执落盘后才归还。

主要决策：

- 一次请求只执行一种语义动作：点击、一次按键/组合键、有限文本插入、有限滚动或一次拖拽。动作内可有多个低层事件，但不能包含“聚焦 → 全选 → 输入 → 保存”这类工作流。
- 不暴露跨请求的 `key_down/key_up/mouse_down/mouse_up`。持键状态不能跨工具调用、模型思考或验证过程保留。
- 多步失败采用 **fail-stop**：停止后续业务输入、尽力释放本次持键、记录部分结果。键鼠操作不具备通用事务回滚能力。
- 输入 API 接受、目标应用消费输入、任务完成三者分开记录。缺证据则 unknown，不能通过日志措辞提升为成功。
- 不自动重试非幂等输入。文字重复、滚动重复、拖放重复与一次失败回执都可能已经产生实际副作用。
- 先补通用取消/释放/去重能力，再逐项上线。建议顺序：无修饰键的有限纵向滚动 → 单次导航键 → 有限文本 → 受限组合键 → 拖拽。各类型独立开关，默认关闭。

这属于第一条线能力扩展。候选编号定位第二条线仍暂缓，参见 [第二条线接口预留](2026-10-30-grounding-second-track-interface-plan.md)。不以新增输入类型为由启动视觉模型实验。

## 3. 请求契约：公共信封 + 有类型动作

### 3.1 公共信封

```text
action_schema_version: 2
request_id, operation_id, request_digest
task_id, harness_session, windows_session, operation_generation
observation_ref: 原图 ID、哈希、尺寸、清单引用、桌面原点
window_context_ref: 窗口实例绑定、context_id、geometry_revision
receiver_ref: 本次输入实际接收区域/焦点的宿主证据引用
authorization_grant, grant_revision
action: 一个且仅一个有类型动作
expected: 后置条件声明与受信验证器引用
policy_version, deadline, limits
```

`operation_id` 是宿主为逻辑动作分配的稳定ID，网络/工具重发沿用它；`request_id` 用于追踪投递。digest对动作内容、目标、观察、约束及授权绑定等规范化内容计算。模型不得自称已授权、已验证或指定放宽策略。

deadline与上限由宿主生成、执行器再限制；实际计时采用本进程单调时钟，不直接比较不同进程的单调时间戳。跨进程传绝对到期时间加最大持续时长，执行器取保守剩余时长；清理另有短的有限宽限期。

接收器字段必须按动作明确，不能仅凭顶层窗口前台就认定文本会进入指定输入框。旧观察可继续用于v1点击；缺少新动作需要的焦点等证据时应生成新观察，不给旧清单补造证据。

解析时拒绝未知动作、未知安全相关字段、互斥字段混搭、非法数值、过长内容和未支持版本；不要忽略模型多传的 `submit=true` 等字段而留下歧义。动作类型不接受任意函数名、Win32 flags、脚本、命令或外部执行路径。

### 3.2 动作联合类型与首批建议上限

上限为初始工程配置建议，不是 Windows 保证或性能实测。宿主可以收紧；放宽需对应测试，不由模型单次请求自行扩大。

| 类型 | 参数建议 | 首批限制 |
| --- | --- | --- |
| click | button、point_original_px | 保持现有单次左键；不顺带开放双击、右键、连点 |
| key_chord | 主键、修饰键集合、键映射模式 | 一次完整按下/释放，禁止 repeat、hold和宏；先无修饰导航键，组合键最多2修饰键且按完整组合白名单 |
| text_insert | 有界字符串、encoding、insert语义 | 首批最多256个Unicode标量且UTF-16最多512单元；单行、短文本、单批先限制16标量；总动作建议10秒以内 |
| scroll | 观察内锚点、axis、notches | 先vertical、每次1–3格、无修饰键；正值向上，负值向下，执行器换算滚轮单位；一次后重新观察 |
| drag | start/end_original_px、button、duration、path_policy | 最后上线；先同一授权窗口/客户区、单显示器、左键、无修饰键、确定性直线路径，建议200–1000ms、最多32移动段 |

组合键总持续建议不超过500ms，不设置模型可控的长按。文本每批必须完成全部对应key-up；实际批大小和检查频率根据支持目标的实测设定。长度上限不能阻止全部风险，还必须绑定接收语义。

一条动作只消费一份当前观察。多个低层事件属于一次手势，不允许每个字符重新消费同一观察，也不允许用这一例外塞入第二个语义动作。动作后需要新观察才能开始下一动作。

## 4. 授权：动作权限和业务后果同时约束

保留用户发放任务范围、窗口/会话、时效和动作集合的模型，新增grant v2细分能力：`key_chord`、`text_insert`、`scroll`、`drag`。`replay`只允许调用已验证程序，不替代程序每一步的动作授权。

grant的附加约束建议包含：允许完整键组合、允许文本接收区域/语义类型、输入长度、滚动轴与上限、拖拽源/终点范围、任务资源边界，以及提交/发送/覆盖等业务后果的允许范围。敏感操作的范围判断由宿主根据真实用户任务与当前证据决定，不能采信模型标签“安全”。

- 在已明确授权范围内不逐键询问用户；现有会话授权可以作为创建更具体grant的依据，但不能把旧grant文件静默升级成宽权限。
- 用户仅要求“填写草稿”不能推导出“发送”；仅有“键盘权限”也不能推导出执行终端命令、批准安装或同意支付。
- Enter、Space、Alt组合、Ctrl+S、Delete、Backspace、Ctrl+A等都可能有副作用，不能按键名一概标成安全。应按接收器状态和目标语义判断。
- `grant_revision`/撤销代次由宿主管理；执行前及分段边界重新验证当前有效授权。撤销后停止业务输入；释放本次持键属于原动作必要清理，不因业务权限撤销而故意留下按下状态。
- v2要求明确Harness会话与Windows会话；执行器从受信启动上下文校验，不能仅比对请求内两个自报字段。当前v1可保留旧行为，新入口不得用空session绕过。

执行器和授权文件属于同用户事故防护边界，不能声称能防御同用户任意本地恶意代码改写程序。无管理员提权、无UIAccess绕过、无改变现有完整性标签。

## 5. 键盘与文本：先确认“输入到哪里”

### 5.1 焦点绑定

在新观察中增加宿主采集的焦点证据：前台顶层窗口、目标线程、`hwndFocus`、菜单/鼠标捕获状态、窗口实例和几何，必要时可附标准UIA焦点元素及可见编辑区域、插入点、选区证据。

`GetGUIThreadInfo`能读取其他GUI线程的焦点信息，但同一个HWND可能包含多个网页/自绘输入框。焦点HWND一致不能证明具体编辑目标一致；需要可见焦点线索或标准可访问性证据补充，不能确认则拒绝文本输入。数据字段不可读与真实不存在分开处理。[GetGUIThreadInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getguithreadinfo)、[GUITHREADINFO](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-guithreadinfo)

需要先点击聚焦时，将点击作为独立动作；之后重新观察并确认焦点再输入。禁止text动作内部悄悄点击、Tab遍历或全选。焦点在同一窗口内跳到另一个输入框，也应停止。

SendInput不支持把输入原子地绑定到指定HWND，检查与发送之间仍有竞态。短批次、实时抢占和复核只能缩小风险，不能消除它。因此首批限制在可见、可确认、无外部提交后果的编辑场景，不声称支持任意软件输入框。

### 5.2 按键/组合键

- 接收语义与完整组合共同入白名单。例如允许编辑区域中一次Left/Right，不等于允许全局快捷键；Tab改变焦点后须重新观察，不直接接着输入文本。
- 首批拒绝Win键、Alt+Tab、Alt+F4、Ctrl+Alt+Del、锁屏/电源键、启动命令界面的组合键、剪贴板快捷键、粘滞键触发序列、持续按键和游戏/Raw Input专用模式。不是永久禁用，是单独能力验收范围。
- Enter/Space、删除/覆盖、保存/提交类组合暂不纳入默认集合；后续有明确目标和后果授权才能启用，且不得与文本作为不可分割宏执行。
- 对快捷键明确采用虚拟键还是扫描码语义，记录目标线程键盘布局；布局变化停止。字符输入不通过猜测键盘布局生成物理键。AltGr、IME组合态、死键状态不支持时明确拒绝。
- 开始前检查相关键、修饰键和鼠标键无用户按住状态，不主动释放用户键，不修改CapsLock/NumLock等切换状态来适配脚本。

### 5.3 文本输入

首选 `KEYEVENTF_UNICODE` 发送字面文本，按UTF-16编码并正确处理代理对，不把字符串当快捷键表达式；每个编码单元有配对事件，分批边界不得切断代理对，组合字符序列尽量保持完整。此方式依赖应用处理VK_PACKET/字符消息，不能声称所有应用都支持。[KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)

第一批只开放无提交意图的短单行文字，拒绝CR/LF、Tab、控制字符、非法代理项；不自动附加Enter、不解释转义宏、不自动切输入法、不清空已有内容。需要多行时后续单独定义多行编辑接收器与换行语义。

`text_insert`的语义是插入，不是设置字段值。若存在选区可能替换已有文本，必须有相应编辑意图和选区证据；首批建议只允许已确认空字段或已确认插入点，不使用隐式Ctrl+A覆盖。

首批拒绝密码、验证码/凭证输入、终端/REPL/命令面板、会随键入产生高影响操作的字段及无法确认类型的输入区。普通“输入文字”授权不能绕过这些边界。对未知控件，输出 `RECEIVER_UNSUPPORTED`，不通过猜测继续。

剪贴板粘贴不是自动备用方案：它涉及用户剪贴板覆盖、历史/同步泄露和恢复竞态，首版禁用。若以后支持，作为独立capability与验收项；遇到用户修改不能用旧内容覆盖恢复。

文本发送中，允许预期的编辑区域变化，不要求每一批之后仍与最初截图逐像素一致。只对稳定上下文/焦点等做阶段检查，编辑区域更新须由动作特定规则解释；不能因此关闭全部图像检查。完成后验证实际新增文字/插入位置，普通“画面有变化”不足以证明文本正确。

## 6. 滚动与拖拽：位置正确也不代表接收器正确

### 6.1 滚动

鼠标锚点在原始观察内，由执行器映射到屏幕；核对前台、命中区域、授权及无修饰键。将移动和悬停导致的目标变化纳入发送前检查，不能认为光标移动没有界面副作用。

首批只发送有限纵向滚轮事件，宿主定义1格对应Windows的120单位；滚动格数不等于像素距离或文本行数，系统和应用设置会改变结果。[MOUSEINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput)

嵌套滚动区、焦点与悬停接收器不同、弹出菜单、未知滚动路由时须有接收器证据；不能确定则拒绝。一次滚动后独立观察该区域的内容/滚动条变化。已在边界可能合法无变化，记录no_change或unknown，不靠无限加大幅度重试。水平滚动、Ctrl+滚轮缩放、惯性模拟、持续“滚到底”后续单独验收。

### 6.2 拖拽

拖拽是一个有界手势，其内部按下—移动—抬起不能拆成模型可控制的多次工具调用。首批仅在可恢复、非文件移动的同窗口场景试验，例如测试画布或低影响滑块；文件拖放、跨窗口/跨进程、外部导入、窗口拖动/缩放、跨屏、自动滚动边缘区和带修饰键的复制/移动拖拽先不支持。

开始前验证源点、终点、整个计划路径及允许操作区；不能只检查两个端点。路径由执行器按固定算法生成，模型不能提交任意长事件序列。动作中每段前检查窗口、几何、捕获状态、用户抢占、期限；未知捕获变化或弹窗遮挡停止移动并进入释放清理。

拖拽期间像素与鼠标捕获的变化可能是预期行为，需单独的状态规则。不能复用点击的全程静态画面要求，也不能简单忽略变化。路径中途移到新区域不能自动扩大授权。

取消时释放鼠标可能立即提交当前位置的drop；把鼠标移回起点或发送Esc也不保证撤销。因此一旦按下后取消，结果必须注明可能已发生部分拖放，停止后验证；不承诺“已回滚”。释放恢复机制未通过崩溃注入测试前，drag保持不可用。

## 7. 取消、key release与崩溃恢复

### 7.1 统一生命周期

```text
received → validated → reserved → input_started → releasing
                                               → observed → finalized
任意阶段取消/异常 → 停止新的业务输入 → releasing → cancelled/unknown
```

所有入口无条件创建本请求取消通道；用户取消、超时、父进程退出、授权撤销、输入抢占都触发同一协作停止流程。每批事件前检查一次；拖拽路径段和文本批次之间必须有检查点。取消只能阻止尚未投递的输入，不能撤回已进入系统队列的事件。

不要一次提交长文本/长轨迹后声称可随时取消。有限组合键可把按下/主键/抬起组成短批次，降低持键窗口，但单次SendInput不等于应用层事务。[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

执行器维护已尝试/已接受事件与可能尚未释放集合。每次执行可能产生down的批次前，先持久化该批次意图；返回后记录接受数量与观察。进程可能在API返回和落盘之间崩溃，所以未完成记录必须按“可能发生”恢复，不能推定没有发送。

正常与可捕获异常路径，在finally中仅释放本动作已按下或有证据可能按下的键/按钮，按逆序释放修饰键。释放不发送新的down、Enter、Esc或Undo，不做业务补偿。部分批次接受时停止剩余业务事件，不按“缺几个事件就补几个”重试原动作。

### 7.2 为什么需要宿主监督

finally无法覆盖强制终止、宿主崩溃或系统掉电。建议在固定Medium执行器体系内增加受信监督/恢复角色：持有输入租约和活动动作记录，监视工作进程退出，必要时调用同一固定执行器的严格 `release_only` 恢复模式。

`release_only`不是模型工具，不接受模型指定键集合，也不能执行正常动作；只能读取匹配原Windows会话/桌面与动作代次的未完成记录。接管前确认原工作进程已退出，或有可证明的fencing使其不能继续输入，避免两个进程交错释放/发送。父进程断开也需触发工作进程停止，不允许失去监督继续执行长动作。

恢复角色只解决尽力清理，不保证绝对释放。发送前日志无法绝对证明down曾发生，用户也可能随后按住同一键；所有权有歧义时不能全键盘清空。停止自动输入，记录 `RELEASE_UNCONFIRMED`，请用户释放相应键/按钮，恢复后重新核对中立状态。不要为避免提示而发送全局Esc或批量松开用户键。

正常业务权限撤销或目标窗口失焦时，仍可在原交互桌面进行必要的自有key-up清理；清理本身可能影响当前前台，必须记录。若已切到锁屏/安全桌面、会话改变或无法确认输入桌面，不跨边界尝试恢复，保留未知状态并阻止后续自动输入。

GetAsyncKeyState的高位可辅助检查当前按下状态，但低位历史标记不可靠，返回0也可能是读取失败，不能单凭全0证明清理成功。[GetAsyncKeyState](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate)

### 7.3 用户抢占与共享桌面

自动化期间监听外来鼠标/键盘事件，只保留计数、时间、类型等最小元数据；不要记录用户键入正文。自有事件可用请求标记辅助归因，但注入标志/标记不是认证机制。任何无法归因的输入按外部干扰处理。

当前last_input_tick相等检查适合开始前辅助判断，分批期间不能继续机械比较初始值，也不能直接忽略所有变化。GetLastInputInfo只提供会话输入时间，且不保证单调，不能区分目标是否消费事件。[GetLastInputInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo)

若采用低层hook，需独立快速消息循环、健康监测；hook可能超时移除。安装/健康未知时，禁止依赖它保证安全的长文本、组合键与拖拽，不把“没有收到事件”当成用户没有抢占。[LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)

本项目控制的所有实例、项目与工具入口应共享同一用户/Windows交互会话/桌面级输入租约。现有项目目录锁不足以覆盖多个项目。锁只约束本系统，不约束其他自动化软件；未知外部输入仍触发停止。绝不屏蔽用户物理输入来维持自动化。

## 8. 幂等：保证不盲目重复，不承诺exactly-once

键鼠输入与本地账本无法组成一个原子事务。目标是持久化去重和不确定时停止，而非声称绝对只执行一次。

- 执行前在持有租约时原子登记 `operation_id + request_digest`，并消费本观察的动作资格。登记失败/磁盘不可写时拒绝发送。
- 同一operation同内容重复请求：已完成返回原回执并标记replayed_receipt；执行中返回in_progress；异常/未知返回unknown_recovery_required，均不再次输入。
- 同一operation内容不同返回 `OPERATION_CONFLICT`。调用方换一个request_id不能规避逻辑operation去重。
- 进程在登记后、发送前崩溃也按可能执行处理；保守停止优于重复输入。新动作需重新观察、核对实际状态并形成新的明确计划。
- 每份观察最多支持一次动作，包含失败途中已移动鼠标的情况。旧 `click.once` 与新消费记录要统一检查，不能让同一观察分别被v1和v2各消费一次。
- 输入完成但回执丢失时，查账本/证据，不重发；不能以重新截图为借口自动重发同一逻辑操作。

文本插入、滚动、拖放都不是天然幂等。未来若要提供“把字段设置为某值”，需要独立的读取—比较—受控编辑—验证协议，不能把text_insert改名后宣称幂等。

## 9. 回执：区分投递、接收和结果

建议回执v2保留以下独立字段，避免一个ok覆盖全部含义：

```text
operation_id, request_id, digest, executor_version, protocol_version
phase, terminal_reason, cancellation_source
input: attempted_count, api_accepted_count, batches_completed,
       external_input_detected, remaining_input_suppressed
delivery: not_attempted | api_accepted | receiver_observed | unknown
release: not_needed | observed_neutral | attempted_unconfirmed | unknown
verification: passed | failed | unknown + verifier/evidence/scope
before_observation, after_observation, receiver_before, receiver_after
pending_or_possible_down, cleanup_attempts
task_success_verified: false   # 执行器不宣告整个任务成功
```

`api_accepted`只表示API报告插入了事件。SendInput返回数量并不证明目标应用响应；UIPI阻断也不会给出可靠的专属错误标识，因此完整性不可读或目标高于Medium时仍须预先拒绝，不能试发判断。[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

`receiver_observed`需要针对接收器的额外证据，不能仅凭光标位置、输入时间、hook看到自有事件或进程exit=0设定。没有这种证据可以如实停在api_accepted，并由独立后置验证判断动作效果，不必伪造接收证明。

| 输入 | 足以支持后续判断的证据 | 不足以证明成功 |
| --- | --- | --- |
| 导航键/组合键 | 预期焦点、选区、菜单或状态变化；对应验证器通过 | OS接受了所有按键事件 |
| 文本 | 接收字段的文本/插入差异与预期一致，校验范围完整；OCR不确定则unknown | 整个窗口像素变化、字符数量相同 |
| 滚动 | 指定区域内容位移或滚动位置变化；边界no-op有明确状态 | 光标没动、输入时间更新 |
| 拖拽 | 对象/选择/滑块的目标状态与原状态关系符合预期 | 鼠标到了终点并松开 |

执行器错误时保留已接受数量、可能副作用与释放情况，不能把计数归零。验证器与模型规划结论分离；一次工具调用被接受不自动让任务completed，也不自动checkpoint为成功。

## 10. 必须fail closed的情况

这里fail closed指：不再发送新的业务输入；若已有自有按下状态，进入有限释放清理；结果不明则禁止自动续跑。它不等于跳过清理直接kill。

| 条件 | 处理 |
| --- | --- |
| 请求版本/参数未知、路径或坐标非法、限额无法解释 | 输入前拒绝，不纠正后猜测执行 |
| grant缺失/过期/撤销，动作、文档、会话或提交后果越界 | 拒绝/停止，不以replay或旧click权限替代 |
| 目标完整性不可读或高于Medium、非原交互桌面/会话 | 拒绝，不提权或后台投递 |
| 窗口身份/实例、几何、前台变化；观察过期/被消费/哈希不符 | 旧请求失效，重新观察与规划 |
| 文本焦点不明、选区/IME/布局状态不支持、输入区类型未知 | 拒绝，不用额外Tab/Enter试探 |
| 用户持键、外部输入/捕获变化、输入监测失效 | 停止业务输入，有限清理，等待恢复 |
| 文本含禁止控制字符、敏感接收区或未知提交语义 | 拒绝当前能力，不降级为剪贴板或物理键宏 |
| 滚动接收器不明，拖拽路径/终点越界或跨越未授权目标 | 拒绝，不自动切窗口/扩展权限 |
| 取消/期限到达、父进程断开、API部分接受、释放无法确认 | 停止并保存部分/未知状态；不自动重试 |
| 动作日志无法持久化、去重冲突、未完成动作未恢复 | 新动作不得开始 |
| 无后置证据、验证failed/unknown、输入回执丢失 | 不执行依赖成功的下一步；核对实际状态 |

## 11. 多步失败与补偿

PreAct仍逐步观察—定位—执行—验证。只有本步骤验证passed且输入中立/收尾完成，才进入下一步；中间结果已提交则如实记录，失败不清空历史。

不自动Ctrl+Z、重新全选删除、反向滚动或拖回起点；这些动作可能撤销用户工作、触发另一条业务路径，且无法保证恢复原状态。未来补偿只能作为独立、显式定义且获准的任务步骤：已知前置状态、适用范围、补偿动作和后置验证。默认仍fail-stop。

新的键盘/文本/滚动/拖拽程序须通过对应动作版本和验证器的重跑验证，proof绑定动作内容、允许参数槽与策略版本。不能让已验证模板接受任意文本或快捷键参数；参数重绑定要有类型、长度、接收区与后果限制。原有点击程序不因文档发布失效，实际语义改变时按版本重新验证，不能批量伪造迁移proof。

## 12. 实施阶段与验收

### E0：先补共同基础

拆分schema版本；统一Node/Python取消与期限；所有异常等待退出或明确标记执行仍未知；增加operation去重与未完成记录；输入租约覆盖本系统全部入口；建立自有按下状态和有限释放恢复机制。现有点击回归必须保持。

### E1–E4：按动作独立上线

E1有限纵向滚动；E2短导航键和受限单行文本；E3明确授权的完整组合键；E4同窗口受限拖拽。每阶段先fake底层事件和故障注入，再用用户允许的空白测试文档/可恢复界面实机验收。完整组合键与drag在恢复监督未通过时保持关闭。

必要测试包括：

1. Node和Python入口一致拒绝旧grant执行新动作；零输入路径可证明。
2. 同顶层窗口内焦点更换、两个输入框、布局变化、遮挡、菜单/捕获变化可触发停止。
3. 每个可能down后的取消、部分接受、异常、强杀、父进程崩溃及重新启动恢复；记录未知，不宣称零输入。
4. 无AbortSignal也能超时退出；取消文件失败、stdout超限、输出损坏、日志写失败不会让新动作抢跑。
5. 同operation重发、不同digest、发送后回执丢失、登记后崩溃、跨项目并发；没有重复副作用。
6. 中英文、非BMP字符、组合字符、非法UTF-16、控制字符和超长文本；不能拆坏代理对或暗中提交。
7. 滚动边界/嵌套区域、拖拽中途取消/捕获改变；禁止自动撤销和无限重试。
8. 用户同时按键时不擅自释放用户键；监测失效、输入桌面改变时禁止后续输入。
9. 观察消费在v1/v2间一致；unknown不进入下一步，不晋升程序、不写成功checkpoint。
10. 真实反例区分“API接受但应用无反应”和“应用达到目标”；只用fake返回成功不足以验收送达。

首轮测试不用重要文档、聊天发送框、终端或文件拖放。记录支持范围、失败分类、取消到停止的实测时延及释放未确认情况；不要把配置中的时间上限当成实测保证。

## 13. 证据与隐私

请求可通过现有stdin传输文本，不放命令行参数、环境变量、异常堆栈或普通日志。正文默认不进入回执和checkpoint；记录长度、编码、操作标识和受控证据引用即可。短秘密的普通哈希也可被猜解，不把哈希当脱敏万能方案。

若审计必须绑定文本内容，用受控存储中的请求或带密钥摘要，遵守授权与保留期限；不让审计日志变成长期文本副本。前后截图可能包含输入正文，也必须沿用截图发送和清理策略。

未解决的活动输入记录不能当临时垃圾删除；恢复完成后按保留策略清理。证据只描述真实观察，不把未知阶段填成成功。

交接结论：在同一Medium执行器中分类型扩展；先把取消、释放和去重闭环补齐，优先有限滚动与短输入，最后拖拽；保持现有授权范围和视觉证据链，任何不确定结果都不得自动续跑或重试。
