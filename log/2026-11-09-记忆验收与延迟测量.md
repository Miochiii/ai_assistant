# 记忆验收与延迟测量

2026-11-09 用户确认：次日自动整理 committed、automatic=1；显式查询内容正确；同工作区新会话不先查询记忆，也能回答常用编辑器。基础自动采纳及跨会话召回验收通过。截图中的一次自然语言回答耗时 55 秒，尚无分段埋点，不能把该次耗时全部归于检索。

## 代码检查

`src/assistant_memory/v2.py` 的 rag_recall 每次通过 subprocess.run 启动 `scripts/memory_rag_worker.py`；worker 完成一次请求即退出。磁盘代次可以复用，但 BGE 和 reranker 的模块级单例随进程退出而消失。配置为 CPU。候选不超过五条时不运行 reranker，超过时执行重排。现场最新 ready.json 的 count 为 15，不能按“昨天只新增一条”把全库当成一条。

面板还依次进行采集、检索、发送前版本检查、模型请求、返回后版本检查。当前 companionStream 收齐并校验完整回复后才展示，因此看到的总等待包含模型完成时间。没有当次分段记录，无法反推 55 秒的各部分占比。

## 本机离线测量

使用相同解释器、模型权重、CPU 配置和检索代码，单独生成合成记忆分区，不读取用户记忆正文。结果均找回合成的 PyCharm 条目。

| 数据量与方式 | 耗时 |
| --- | ---: |
| 1 条，新进程第 1 次（创建测试索引） | 14.192 秒 |
| 1 条，新进程第 2 次（复用磁盘索引） | 13.761 秒 |
| 1 条，同一进程首次（索引已存在，模型未加载） | 12.686 秒 |
| 1 条，同进程第二次（模型已加载） | 0.051 秒 |
| 15 条，同进程首次（建索引、加载模型、检索及重排） | 15.634 秒 |
| 15 条，同进程第二次（复用索引及模型，检索及重排） | 0.644 秒 |

这是小样本顺序计时，不是 P50/P95，也不包含真实 DS API 调用。15 条首轮与次轮之间同时存在建索引和模型加载差异；单条“已有索引但新进程”对照进一步支持重复加载开销显著。不能承诺真实对话总时延降为上述数字。

两次测试均在 finally 中校验路径后清理自己的索引分区，没有安装依赖、改原 RAG 环境或请求付费 API。本轮只完成分析与测量，尚未把生产 worker 改为常驻。

## 推荐实施顺序

1. 增加分段时延记录：SQLite/采集、worker 启动与模型加载、embedding、rerank、DS 首字/完整响应、版本校验、总时延。只记录时长、数量、引擎与错误码，不写对话正文。先辨别冷请求和热请求。
2. 改为 Host 管理的本地常驻检索 worker，使用带 request_id 的标准输入输出协议，不暴露网络端口。复用模型单例；先保留逐请求打开/关闭 Qdrant 和现有代次锁，降低一次改造范围。设置单飞队列、超时、崩溃重建、关闭及空闲退出策略。
3. SQLite 继续做权威状态。Host 每轮取得当前作用域有效快照，worker 仅返回候选 ID，注入前重新验证当前版本和有效性。不得为了缓存命中而删除撤销、作用域及版本校验。知识配置/模型 profile 变化重启 worker；结果缓存需绑定 scope、版本、query、profile，第一版可以不缓存结果。
4. 不在本轮同时更换 embedding、量化或引入 CUDA。先利用已有模型复用；后续按埋点判断是否值得扩大 reranker 调度优化或做精确查询直达。
5. 感知反馈可显示“检索记忆/生成回复”等短状态。提前流式显示正式正文需额外解决撤销发生在生成期间的问题；不能移除当前返回后版本复查来换取表面速度。

性能优化后再扩大事实/事件自动采纳、冲突归一及物理删除覆盖。当前基础跨日记忆已验收，优先消除每轮重复加载这一日常使用瓶颈。
