# 技术决策：记忆历史残留、干净上下文与 surface 重建

日期：2026-10-30（UTC+08:00）  
项目：`E:\file\agent\ai assistant`  
接收者：DeepSeek 后续开发  
状态：设计决策，待实施和验收。本轮仅新增本文，不修改正式开关、历史、记忆数据库或宿主源码。

## 1. 本次决定

**当前采用“显式 recall/resume + 失效时切换干净上下文”；正式 auto_recall 继续关闭。长期目标为可验证的 surface 重建，不采用每轮都新建会话。**

显式 recall 降低无意注入的范围，但不消除历史残留。因此，“继续显式 recall”必须与暴露记录、失效阻断和干净上下文回退一起设计，不能被解释为已有彻底撤销能力。

当前已启用的项目自动 checkpoint 按既有同意继续运行，不因第二批暂缓而关闭。自动 checkpoint 的同意不覆盖自动检索/注入，也不覆盖删除历史或扩大授权。

本决策补充并收紧[上一份自动化日志](<E:/file/agent/ai assistant/log/2026-10-29-memory-automation-and-executor-review-decision.md>)中“清缓存与失效后续注入”的实现要求：必须处理完整有效上下文中的残留，而不仅是新的 context 贡献。

## 2. 已确认的前提与证据边界

已安装 Harness 的原生夹具表明：

- `systemPrompt.context` 能生成来源为 `runtime-context` 的数据贡献；没有把正文加入 system/developer。
- 清空贡献之后，同一轮下一次工具循环，以及下一条用户请求，仍在请求历史中携带先前正文。
- `llm/stream` 可观测交给适配器的请求，但不证明远端实际接收，也不意味着它能单独修复持久化历史。

证据：[入口核对说明](<E:/file/agent/ai assistant/docs/memory_context_hook_audit.md>)、[原生夹具结果](<E:/file/agent/ai assistant/results/memory/context-hook-audit-20261029.json>)、[检查脚本](<E:/file/agent/ai assistant/scripts/check_dsh_memory_context.mjs>)。

原生夹具使用真实 AgentLoop 和假模型，共三次请求、零网络；它验证的是“清贡献不足以清历史”，不是完整 forget 流程或线上清理成功。本轮没有重新执行该夹具。

当前状态以[宿主接入说明顶部更新](<E:/file/agent/ai assistant/docs/memory_host_integration.md>)及实际代码为准：auto_checkpoint 已有 live 证据，auto_recall 未启用；不要依据历史条目重新实现已有功能。

## 3. 先定义承诺：停止使用不等于抹除历史

本文中的 surface 指**下一次真正提交给模型的完整有效上下文**，包括历史消息、工具结果、自动摘要、当前动态贡献、附件引用及可能的服务端续接状态；不只是聊天界面可见的文本。

需要区分四个层面：

| 层面 | 本次要求 |
| --- | --- |
| 核心记忆状态 | 撤销/删除/到期后按核心规则不可再召回 |
| 本地未来模型请求 | 不再携带由失效记忆注入或派生的内容；无法保证则先阻断受影响上下文 |
| 历史展示、日志与导出 | 是否保留单独说明；保留不代表可以再次参与推理 |
| 已发请求、服务端副本 | 不能追溯收回；不宣称删除已发送的内容 |

这是一项来源与数据流承诺，不是声称模型从此不可能产生相同文字。用户后来独立提供同样信息，或模型从别的合法来源知道它，属于不同来源；不得靠全局字符串替换删除用户原始消息。

关闭 auto_recall 只代表停止自动召回，不默认删除已经提供的上下文。若用户要求“后续不再使用已有记忆”，则需触发本文的失效/清理流程，不能只关开关。

## 4. 三条路线及最小条件

### A. 显式 recall/resume：当前默认路径

“显式”指有一次独立、可追踪的记忆工具调用，不要求用户每次手动输入 `/memory`；保留现有模型工具权限，不增加无意义的逐次确认。

最低条件：

1. 每次工具调用检查 scope、有效时间、版本、撤销/删除状态；默认不混入候选与历史版本。
2. 记录哪些记忆版本进入了哪个会话、请求、工具结果及摘要。resume 返回的 checkpoint 和父依赖同样登记。
3. 任何受影响记忆失效后，将相关上下文标记为需清理；不仅停止新 recall。
4. 清理或干净切换完成前，不再从该上下文提交新的模型请求。
5. 无法证明旧历史暴露范围时，保守将该会话视为受影响，而非“没有记录所以未暴露”。

限制：recall 工具结果、assistant 复述以及工具参数中的派生信息都可能残留。仅显式 recall 并不天然比自动注入更容易删除；它主要减少默认暴露面。

### B. 干净上下文：失效时的必要回退

不每轮重开。删除、撤销、相关记录到期、事实修订使旧版本不再适用，或作用域改变且不能安全隔离时，检查是否需要切换。只有未暴露的记忆失效，不必清空无关会话。

最低条件：

1. 新执行上下文不继承旧 messages、自动压缩摘要、工具结果或服务端续接链；新 session ID 本身不是证明。
2. 初始化时复核 auto_recall/其他提供器，不能把刚失效的内容重新加入。
3. 交接只带独立核验的最小信息：用户确认的目标、运行 ID、当前有效的任务状态与证据引用。
4. 交接字段也要逐项检查依赖。不能因字段来自“宿主账本”就忽略它可能含有从失效记忆派生的文件名、目标或摘要。
5. 不让旧会话生成总结后原样复制。无法证明交接干净时，宁可只保留不含正文的标识，请用户补充必要目标。
6. 不继承旧窗口坐标、已消费观察或执行授权；按既有协议重新核对，不能重新执行已经完成的动作。
7. 用户可见历史与新执行上下文的关系清楚；旧记录如仍保留，标记为历史、不参与新请求。

不得假定当前 Harness 已支持这些能力。先核对真正的新建/初始化/恢复接口；无稳定接口时由用户新开会话，不修改安装包、不伪造消息来源。本文不授权后台擅自创建大量会话。

可选未来试验：每个独立任务使用干净隔离会话，并在任务结束后释放有效上下文。这可降低跨任务残留，但任务内失效仍要处理；需要单独的自动注入同意和隔离验收。

### C. surface 重建：长期方向，先验证可行性

目标是保留合理对话连续性，同时重建下一次提交的上下文。它不能只是删除 `runtime-context` 标记的消息。

最低条件：

1. 能追踪原始注入和派生节点，包括 assistant 复述、工具参数/结果、压缩摘要及 checkpoint。
2. 能排除失效节点及其受影响派生内容；无法精确证明依赖时，保守丢弃整个片段/后续区段，或回退干净上下文。
3. 保持工具调用与结果合法配对，不伪造用户消息、来源和历史动作。
4. 重建不修改任务已经实际执行的事实；历史审计可保留，但不能因保留审计又被自动重新导入模型。
5. 更新会话恢复、压缩、工具循环和重试路径，避免它们从旧历史重新构造污染 surface。
6. 新 surface 构建、版本复核及发布有明确原子边界；发布失败不能回退发送旧 surface。
7. 可信请求出口仍核验当前版本和有效性；不能绕过统一入口另发模型请求。
8. 有宿主支持的持久化/恢复契约和版本兼容策略，不依赖一次性的安装包热补丁。

如果用户继续指令依赖被丢弃的内容，例如“照刚才那个做”，必须澄清缺失信息，不能在后台偷偷取回被排除的历史。

`llm/stream` 过滤可作为最后一道校验/拦截，但单独使用它不足以解决持久化、重试、派生摘要和恢复路径。只有整个重建链路验收通过，才允许宣称后续请求不再携带失效内容。

## 5. 建议的数据与状态模型

先复用已有 memory ID、版本、依赖关系和真实请求 ID，避免第二套记忆真源。以下是概念字段，不是已实现 API：

```text
ContextExposure
  user_scope, project_scope, session_id, request_id
  context_generation
  memory_ids_and_versions
  surface_node_ids, derived_node_ids
  stage: prepared | submitted_to_adapter | invalidated

ContextState
  generation
  status: clean | needs_refresh | rebuilding | blocked
  invalidation_event_ids
  memory_state_revision
```

暴露登记不复制正文。准备失败/提交未确认时允许保守扩大暴露范围，不能把没有远端回执等同于没有发送。所有受影响会话均需处理，不只处理当前前台会话。

关闭应用或崩溃后，这些失效标记必须可恢复。无法读出旧记录时，不自动恢复旧 surface 为 clean。

### 失效流程

```text
记忆修改/撤销/删除/到期被确认
  → 更新核心状态，并持久化可恢复的失效事件/版本
  → 标记受影响上下文 needs_refresh，停止提交旧版本请求
  → 清除待注入批次与可控缓存；处理正在运行的旧版本请求
  → 尝试受支持的 surface 重建
      成功：验证 → 发布新 generation → clean
      不支持/失败/依赖不完整：切换干净上下文或 blocked
  → 后续每次请求（含重试/工具循环）再次检查 generation 与有效状态
```

到期没有用户命令事件，也必须在请求准备和提交边界检查。纯后台清理定时器不能作为唯一保障。

核心状态更新与会话存储可能跨系统：使用事务内持久化的失效事件/版本再可靠消费，或等价可恢复机制。若无法保证通知送达，请求出口须检测未处理版本并保守阻断；不能出现“库已删除，宿主因漏通知继续发送”的窗口。

## 6. 请求并发、取消与迟到结果

为同一上下文的发布与提交定义统一顺序。请求捕获 generation 和记忆状态版本；提交前在同一受控关口核验。不能“检查完成 → 失效已提交 → 旧请求仍发送”而无处理。

失效时：

- 尚未发送的旧请求取消，包括排队重试。
- 已发送请求尝试取消；取消不保证远端未处理。
- 无法取消的迟到结果可以作为隔离诊断记录，但不得自动驱动新动作、写入派生记忆或加入干净上下文。
- 已经发生的桌面动作保留真实回执。若存在在途执行，按执行器取消/收尾协议处理，不假装回滚，不为补写日志重试输入。
- 后续自动 checkpoint 只能按真实来源与依赖保存；失效结果不能作为新的可信事实被重新包装。

保证范围以受控请求提交的实际顺序为准，不声称能撤回失效前已经发出的内容。状态迁移和请求出口需要并发测试，单线程演示不能证明竞态已解决。

## 7. 本阶段实施顺序

### C0：维持正式状态

- 保持 `auto_recall=0`，保留用户已启用的 auto_checkpoint 和原有保留期限。
- 不重复索取已有 checkpoint 同意，也不将其扩展为自动注入同意。
- 显式 recall/resume 仍可使用，但明确目前的历史残留限制；受影响会话在清理能力未具备时采用新上下文继续。

### C1：先补暴露登记与失效闸门

把 recall/resume、未来自动注入、摘要和 checkpoint 的依赖接到同一请求链。实现失效事件、请求版本检查、重启恢复；字段/异常结果经现有协议返回。

先在隔离夹具中测试，不为测试读取正式记忆正文。历史旧会话没有暴露元数据时使用保守回退，不能把追踪范围声明为完整。

### C2：完成最小干净切换

验证宿主提供的新上下文能力，检查新会话初始化、摘要注入和服务端续接参数。只交接最小可信信息；创建能力不足时保留人工新开会话路径，不临时改宿主安装包。

### C3：surface 重建可行性验证

沿用真实 AgentLoop + 假模型方式，完成下一节的离线矩阵。先产出支持的接口与证据，不先大规模改造 Harness。

如果宿主无法稳定支持重建，明确结论为“不支持，使用干净切换”，无需为了自动检索重写整个 Harness。若支持，再单独实现可维护的适配与版本锁定。

### C4：重新评估自动注入上线

只有 C1/C2 与选定策略的请求边界验证通过后，才进入正式 auto_recall；启用范围、历史残留说明、关闭语义和回退行为需要用户可见。重建尚不可靠时，不将自动注入接到长期复用的生产会话。

## 8. 最小验收矩阵

使用独立数据库、合成记忆和假模型；捕获真正交给适配器的完整请求，并同时检查恢复用会话状态。以下测试不能仅凭 UI 消息消失判断通过。

| 场景 | 通过条件 |
| --- | --- |
| 清贡献、清召回缓存 | 如仍有历史正文，正确报告能力不足，不误报已清理 |
| recall/resume 暴露后撤销/删除 | 下一受控请求不含失效来源及受影响派生片段，或明确阻断 |
| 下一工具循环、同轮重试、新用户请求 | 三条路径均受版本检查，不绕过闸门 |
| 记忆到期/被新版本替代 | 自动检查有效性，旧值不继续作为当前有效信息发送 |
| assistant 改写、翻译或摘要了原记忆 | 依据依赖清理，而不只匹配原始字符串 |
| 工具参数/结果含派生值 | 受影响内容清理且调用配对仍合法 |
| 自动压缩/重启恢复/后台旧任务 | 不从旧历史重新引入失效内容 |
| 多会话同时暴露同一条记忆 | 受影响上下文全部失效，无关上下文不被误清空 |
| 删除与请求提交并发 | 提交顺序明确；失效后的新请求无法使用旧版本 |
| 取消失败、旧请求迟到 | 不自动执行动作、不重新写入失效派生记忆 |
| 切换新 session 但继承旧摘要 | 测试必须判失败，而不是因新 ID 判干净 |
| surface 发布失败/依赖缺失 | 保持 blocked 或干净回退，不发送旧 surface |
| 原用户消息独立包含相同字符串 | 不伪造来源、不机械删除用户原话；删除范围说明准确 |
| 旧正文仍保留在历史展示/导出 | 不再进入有效请求；明确不等于物理删除外部副本 |

可在合成记忆中放置唯一标记检查直接泄漏，同时预设无原标记的改写/摘要节点测试依赖失效。字符串扫描只能发现部分残留，不能单独证明语义去污染；无法追踪时应丢弃更多上下文或干净切换。

通过离线矩阵后，再做一次有限现场验证，分别记录接口完成、插件加载、真实触发和请求出口观察。不得把本地 `submitted_to_adapter` 写成远端服务已擦除或模型已完全忘记。

## 9. 向用户展示的状态与交付

建议区分：

- “已停止自动召回”：只是开关状态。
- “记忆已撤销/删除，当前上下文需要刷新”：核心变更已完成，不能继续旧请求。
- “已切换干净上下文，可继续”：完成对应验证，旧历史是否保留另行说明。
- “当前宿主无法安全重建，请新开会话继续”：明确限制，不说删除失败或已经完全清除。

不把一句“请忽略旧记忆”作为任何清理步骤；模型提示不能代替数据流隔离。

最终交付包含：选定策略、实际宿主接口、暴露/失效字段、并发顺序、请求与恢复测试证据、未支持路径及用户可见语义。完成后统一更新日志；测试临时会话/数据库定向清理，正式历史、用户记忆和桌面证据不在本轮擅自删除。
