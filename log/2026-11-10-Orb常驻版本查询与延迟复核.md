# Orb 常驻版本查询与延迟复核

承接真实版本接入与跨进程互斥。本轮消除每个流片段检查都启动 Python 的开销，正式 Orb/profile/记忆数据库保持不变。

## 实现

- `scripts/memory_generation_worker.py`：只接受空查询的逐行 JSON 协议，启动参数由 Host 固定数据库、用户、项目和工作区。每次请求重读配置、核对工作区、重新打开 SQLite、计算当前有效集合版本后关闭连接；不缓存版本或正文，不加载 BGE/重排模型。
- 复用已有 MemoryRagClient 的串行 stdio 运输层，仅新增可配置的脚本入口与启动参数；原 RAG 路径默认值不变。配置、数据库、作用域、解释器变化会改变进程 profile 并重建 worker。
- `createMemoryHost` 新增可选 `residentGeneration`；默认关闭以兼容旧调用。`generation-host.js` 明确启用常驻路径。现有单次 CLI 保留。
- 每次查询截止时间 15 秒（包含排队），空闲 5 分钟退出；排队取消不杀其他请求，在途取消/超时/退出导致失败并释放进程，下次查询重建。Host 卸载终止两个独立 worker。版本查询错误不回退旧 token。
- Orb 的 pre-step/流片段门禁传递请求取消信号。开发副本已通过 manifest 校验同步薄适配代码；实际查询逻辑仍来自 E 盘独立插件。

## 本机结果

同一个真实 SQLite + 当前 Harness SDK + 模拟 Orb runtime 夹具，5 次假模型请求、25 次版本检查：

| 方式 | 25 次检查累计 | 最大单次 |
| --- | ---: | ---: |
| 每次启动 CLI（前轮） | 4351 ms | 184 ms |
| 常驻轻量 worker（本轮） | 293 ms | 167 ms |

累计下降约 93%，包含首次冷启动；不是用户真实聊天 P50/P95，也不是完整模型响应速度承诺。没有减少版本检查次数。随着有效记忆数量增加，计算有效集合指纹的成本仍可能增长。

报告 `results/memory/orb-cutover-resident-sqlite-native-20261110.json` 确认：旧通知拒绝、新会话与恢复上下文干净、真实 consent 变化导致失效、推理中变更后的工具调用被阻止。SDK 是真实安装版；Orb runtime/UI 仍由夹具模拟。

## 验证与协议边界

- 27 项相关 Node 测试通过：Host、共用运输层和切换事务。包括串行复用、排队/在途取消、错误响应 ID、退出、超时、profile 变化、空闲回收及卸载拒绝。
- `check_orb_generation.mjs` 真实子进程/SQLite 验证通过：同 PID 复用、只读版本查询载荷、不接受写入请求、配置损坏拒绝且修复后可恢复、超过 8192 字符的输入使 worker 退出并在下次查询重建、关闭/开启/global disable 和异工作区拒绝。
- worker 响应只有请求标识、状态与版本元数据；错误不输出正文、SQL 或原异常内容。这里的“版本查询”不代表 SQLite 操作系统只读连接，MemoryGateway 仍保留原初始化表行为；本轮仅使用临时测试库。
- 取消信号接入后，非 SQLite 原生夹具再次通过。真实常驻 SQLite 基准见上述独立报告。
